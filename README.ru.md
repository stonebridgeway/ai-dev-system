> 🇷🇺 Русский (эта страница) · 🇬🇧 English version: [README.md](README.md)

**Локальный слой для AI coding agents: постоянная память о проекте, нужные для
задачи skills, контролируемый жизненный цикл работы и завершение, которое агент
обязан доказать.**

Работает на вашей машине по `stdio` — без сетевого порта, без удалённого сервера,
без аккаунта. Вы направляете на него MCP-клиент, которым и так пользуетесь
(Claude Code, Claude Desktop, Cursor, VS Code, Codex, Gemini), и агент в этом
клиенте получает четыре вещи, описанные ниже.

![Настольное приложение AI Dev: проект с задачами, решениями и передачами между сессиями](docs/images/app-projects.ru.png)

## Что нового в 3.0

3.0 меняет то, как AI Dev ставится и как AI-клиент до него добирается, — а не то, что агент с ним
умеет. Сервер тот же, что знают пользователи 2.x; новое — вход.

- **Два продукта из одной системы.** **Настольное приложение** для человека за своим компьютером и
  **сервер для ИИ-агентов, который целиком настраивается из терминала**: `ai-dev` без аргументов
  открывает меню над всеми настройками, а те же команды работают из скрипта и по SSH.
- **Без Python.** Поиск, его индекс и гибридное ранжирование работают в Node; локальная модель
  BGE-M3 — ONNX-экспорт, который скачивается с прогрессом и докачкой и сверяется пофайлово.
- **Один демон на всех клиентов.** Индекс и модель грузятся один раз: три клиента занимали 528 МБ,
  теперь — 391 МБ.
- **Ответы, которые агенту по карману.** Инструменты задачи отвечают тем, что изменилось, а не всей
  записью каждый раз: задача из [демо](docs/ru/DEMO.md) стоит 33 КБ ответов вместо 242 КБ.
- **Docker как режим сервера.** Каждая сессия — свой контейнер, старт около секунды; образ — 716 МБ
  (у 2.x — 1,84 ГБ).
- **614 отобранных skills** вместо 3 228 — коннекторы урезаны до тех, что нужны разработчику, а
  качество маршрутизации и поиска не изменилось.

Переход с 2.x: [Переход с 2.x на 3.0](docs/ru/MIGRATION.md). Все изменения: [CHANGELOG](CHANGELOG.md)
*(на английском)*.

## Проблема

Coding-агент способный и беспамятный. В каждой сессии он:

- **начинает с нуля** — не помнит вашу архитектуру, ваши соглашения и решение,
  принятое на прошлой неделе, поэтому проект приходится объяснять заново;
- **угадывает подход**, потому что ничто не ведёт его от «добавить авторизацию»
  к знаниям, которые к авторизации относятся;
- **работает без формы** — нет явного начала, нет чекпоинтов, нет пути назад,
  когда ход пошёл не туда;
- **и сообщает, что закончил.** *«Должно работать».* *«Это pre-existing issue».*
  *«Тесты пока пропустим».*

Дорого обходится последнее. Сделанная задача и уверенная фраза выглядят
одинаково, а что из этого вам досталось — выясняется позже.

## Что происходит после установки

Одна задача от начала до конца. Это и есть весь продукт:

```mermaid
flowchart LR
    A["Вы: добавить авторизацию<br/>в API"] --> B["begin_task<br/><i>грузит контекст проекта:<br/>стек, соглашения,<br/>прошлые решения</i>"]
    B --> C["выбирает 3 skills<br/><i>из 614</i>"]
    C --> D["агент пишет<br/>код"]
    D --> E["checkpoint_task<br/><i>+ снапшот<br/>рабочего дерева</i>"]
    E --> F["verify_task<br/><i>тесты, quality gate,<br/>скан безопасности</i>"]
    F -->|не прошло| D
    F -->|прошло| G["complete_task<br/><i>отказывает отчёту,<br/>который не подтверждён</i>"]
    E -.->|ход пошёл не туда| H["rollback_task"]
    H -.-> D
```

Четыре вещи, которых агент раньше не умел:

| | |
| --- | --- |
| 🧠 **Он помнит проект** | `begin_task` компилирует пакет контекста: стек, соглашения, записанные архитектурные решения, передачу из прошлой сессии и инстинкты, накопленные между сессиями. Объяснять заново не нужно. |
| 🎯 **Он находит подходящие знания** | Гибридный поиск (ключевые слова + sparse + опциональная локальная BGE-M3) направляет запрос максимум к трём skills из 614 — достаточно, чтобы помочь, и мало, чтобы уместиться в контекст. |
| 🔒 **Он работает внутри жизненного цикла** | Начать, зачекпоинтить, проверить, завершить. Каждый чекпоинт снимает снапшот рабочего дерева, поэтому любой ход можно отменить, не трогая ветку, stash и индекс. |
| ✅ **Он не может просто заявить, что закончил** | `complete_task` сверяет отчёт с проверками, которые действительно выполнялись. «Должно работать», «pre-existing issue», «тесты пока пропустим» возвращаются отказом с названием правила и тем, чего не хватает. |

**→ [Посмотреть на настоящей задаче](docs/ru/DEMO.md)** — «добавить авторизацию в
API», по шагам, включая падение проверки и исправление.

## Установка

Три способа, одна система — выбирайте по тому, что у вас есть:

| | |
| --- | --- |
| **Настольное приложение** — Windows, Linux, без терминала | Скачайте пакет для своей системы из [релизов](https://github.com/stonebridgeway/ai-dev-system/releases): `AI-Dev-Setup-<версия>.exe` или AppImage / `.deb`. Без Node, Python и Docker: приложение несёт свой Node. |
| **Сервер для ИИ-агентов, из терминала** — Linux, Windows | `npx ai-dev-system setup` — Node.js 22.16+ (или 24+), и больше ничего. |
| **Docker** — сервер в контейнере | `sh ./bootstrap.sh` на Linux, `bootstrap.ps1` на Windows, при запущенном Docker; на Windows ещё нужны Node.js 22.12+ и клон репозитория — конфиги клиентов пишет Node. Для машины, на которой не должно быть личного vault, или для команды, которой нужен один образ на всех. |

**macOS в разработке.** Его код есть в репозитории, и CI гоняет его тесты на Mac, но в релизе 3.0
приложения для Mac нет, а установка из терминала и через Docker на Mac пока не поддерживается.

### Настольное приложение

Запустите установщик на Windows (для вашей учётной записи, без администратора) или AppImage либо
`.deb` на Linux. Первый запуск готовит рантайм и открывает мастер: папка, где лежат ваши проекты,
AI-клиенты для подключения, локальная модель и поисковый индекс. Перезапустите подключённых
клиентов — это вся установка. Приложение на Windows и AppImage обновляются сами из релизов.

![Мастер первого запуска: папка проектов, AI-клиенты, локальная модель, индекс](docs/images/app-wizard.ru.png)

Дальше его экраны меняют всё: состояние установки, ваши проекты с задачами и решениями, навыки — и
ваши собственные, из папки, по шаблону или из репозитория на GitHub, — правила защиты, хуки и
инженерные правила репозитория, MCP-серверы, которые запускают ваши клиенты, и настройки. Подробнее —
[Настольное приложение](docs/ru/DESKTOP.md).

### Из терминала

```bash
npx ai-dev-system setup
```

`setup` ставит свою копию в `~/.ai-dev`, спрашивает, подключить ли найденных AI-клиентов — Claude
Code, Claude Desktop, Cursor, VS Code, Codex и Gemini CLI — и скачать ли локальную модель поиска
(`--yes` берёт ответы по умолчанию: клиенты — да, модель — нет), строит поисковый индекс и
подключает клиентов. Каждый клиент получает одну запись, `ai-dev`, которая запускает ваш Node по
полному пути, поэтому её находит и клиент, открытый из меню «Пуск» или ярлыка на рабочем столе.
Остальные серверы в этих файлах остаются как были, перед изменением каждый файл сохраняется в
резервную копию, запись `ai-dev-system` из 2.x заменяется, а повторный запуск ничего не меняет.
После этого перезапустите клиентов — это вся установка.

Потом `ai-dev` без аргументов открывает меню над всеми настройками — каждый пункт показывает команду,
которую выполняет, чтобы то же можно было вписать в скрипт, — а `ai-dev settings`, `skills`, `rules`,
`servers` и `status` делают это напрямую, и по SSH тоже
([Настройка сервера из терминала](docs/ru/INSTALL.md#настройка-сервера-из-терминала)).

![Меню ai-dev в терминале и MCP-серверы репозитория с тем, что в них проверить](docs/images/terminal-servers.png)

Поиск, гибридное ранжирование, галактика знаний и подготовка проекта работают в Node. Python не
обязателен: скрипт на Python запускают два инструмента — `query_ui_ux_knowledge` и
`generate_ui_ux_design_system`, работающие с набором UI UX Pro Max, — и без Python они так и
отвечают. Локальная dense-модель — один флаг, `setup --model`: пиннутый ONNX-экспорт BGE-M3 со
сверкой sha256, работающий в Node; оборванная загрузка продолжается с места обрыва, а
`AI_DEV_MODEL_MIRROR` и `HTTPS_PROXY` учитываются.

### Docker

`bootstrap.sh` (`bootstrap.ps1` на Windows) проверяет, что Docker отвечает, скачивает образ,
проверяет, что сервер в нём отвечает на MCP-рукопожатие, и пишет каждому найденному AI-клиенту
запись, которая сама запускает `docker run -i --rm …`: каждая сессия — свой контейнер, а между
сессиями ничего не работает. Ваши данные лежат в томе `ai-dev-system-data`, а сервер видит только
папку проектов, которую смонтировал bootstrap. Один `docker run … ai-dev model install` кладёт
локальную модель в том. Подробности: [Docker](docs/ru/INSTALL.md#docker).

Блоки конфигурации для каждого клиента, локальная модель, обновление с 2.x, удаление и что делать,
если не заработало: **[docs/ru/INSTALL.md](docs/ru/INSTALL.md)**. Работа над самим AI Dev, из клона:
[CONTRIBUTING.md](CONTRIBUTING.md) *(на английском)*.

## Первая задача

Откройте репозиторий в клиенте и скажите:

```text
Используй MCP-сервер ai-dev. Начни задачу для ~/Dev/my-project:
добавь экспорт отчёта в CSV, покрой изменение тестами и выполни verify_task.
```

С Docker сервер видит только папку проектов, которую смонтировал bootstrap, — `AI-Dev-Projects` в
домашней папке, если `--project-path` (`-ProjectPath` на Windows) или записи, которые bootstrap
заменил, не назвали другую, — поэтому
держите проект там. На Linux сервер видит его по своему пути; на Windows он видит эту папку
как `/workspace`: называйте проект `/workspace/my-project`.

Что вы должны увидеть: агент вызывает `begin_task`, показывает собранный контекст
и выбранные skills, пишет код, ставит чекпоинт, запускает `verify_task` и только
после этого закрывает задачу — с описанием pull request, собранным из
доказательств в `.ai-dev/pr/<task_id>.md`. В репозитории, которого AI Dev ещё не
видел, он сначала вызывает `prepare_project`: тот пишет `AGENTS.md` и проверки,
которые запускает `verify_task`, — `.ai-dev/quality-gate.md` — из скриптов
самого проекта.

Если он попробует закрыть её раньше, ему не дадут. В этом и смысл.

## Что вы получаете

Агенту сервер отдаёт 135 инструментов (и ещё 16 — [control API](ai-dev-mcp-server/docs/CONTROL-API.md) — приложению, которое их попросит). Знать их не нужно — они собраны в восемь
**профилей возможностей**, и на критическом пути только `core`:

| Профиль | Инструментов | Что добавляет |
| --- | --- | --- |
| **`core`** | 25 | Контекст проекта, маршрутизацию skills и задачу от первой команды до подтверждённого завершения. *Всегда включён.* |
| `coding` | 18 | Эпики, plan gate, карточки проекта и инженерные правила репозитория. |
| `memory` | 17 | Решения, передачи между сессиями, инстинкты, накопленные со временем, и 3D-галактика хранилища, по которой можно летать. |
| `git` | 9 | Изолированные worktree, снапшоты и откат, разбор диффа, текст pull request. |
| `frontend` | 13 | Бриф, визуальные направления, дизайн-систему, референсы. |
| `qa` | 8 | Playwright и визуальный QA, а также бенчмарки поиска и маршрутизации. |
| `security` | 9 | Сканы секретов и зависимостей, планы исправления зависимостей, политику команд и записи, инвентаризацию MCP. |
| `advanced` | 36 | Диаграммы, индексы поиска и skills, дашборд, расходы, упаковку runtime. |

Задайте `AI_DEV_PROFILES=core,git` — и сервер объявит 34 инструмента вместо 135:
около 34 КБ схемы `tools/list` для клиента вместо 141 КБ (замерено, команда —
в [Возможностях](docs/ru/CAPABILITIES.md#сколько-это-экономит)), ещё до того как модель прочитала
ваш запрос. Если переменная не задана, включено всё и ничего не скрыто — если только профили не
выбраны в настройках (`profiles` в `~/.ai-dev/config.json`, их пишет настольное приложение): они
заполняют незаданную `AI_DEV_PROFILES` для каждой команды `ai-dev`.

**[docs/ru/CAPABILITIES.md](docs/ru/CAPABILITIES.md)** — что несёт каждый профиль
и когда его включать.

## Как это устроено

```mermaid
flowchart TB
    subgraph client["Ваши MCP-клиенты (Claude Code, Cursor, VS Code, Codex, Gemini)"]
        agent["агент"]
    end
    agent <-->|stdio, без сетевого порта| entry["запись ai-dev<br/><i>одна на клиент</i>"]
    entry <--> daemon["демон ai-dev<br/><i>один на всех клиентов:<br/>135 инструментов в 8 профилях</i>"]
    app["Приложение / ai-dev CLI"] -.->|control API| daemon
    daemon --> ctx["Контекст проекта<br/><i>стек, соглашения,<br/>решения, передачи</i>"]
    daemon --> skills["Библиотека skills<br/><i>614 skills,<br/>гибридный поиск</i>"]
    daemon --> life["Жизненный цикл задачи<br/><i>снапшоты, quality gate,<br/>линтер завершения</i>"]
    ctx & skills & life --> disk[("Только ваша машина<br/><i>~/.ai-dev + .ai-dev/ в репозитории</i>")]
```

Всё локально и читаемо: состояние проекта лежит в `.ai-dev/` внутри репозитория
(его видно в pull request), личная память — в `~/.ai-dev/`. В Docker-образе нет
ни vault, ни токенов, ни проектов, ни истории задач, а контейнер работает без
сети, без capabilities и с файловой системой только для чтения.
