## 1. Поток работы

```
ПК (GPT пишет код, владелец тестирует)
  └─ ветка fix/… или feat/… от develop форка
       └─ develop форка  ──(когда всё зелено)──►  main форка
                                                  └─ PR BreezeAreaSay:main → stonebridgeway:main
                                                       └─ CI прода зелёный → merge (публикует только :edge)
                                                            └─ freeze-2x (руками) → тег v3.0.0 в проде
                                                                 └─ образы + draft release → npm publish → опубликовать release
```

Рабочие документы (этот план, журнал дефектов) живут в `develop`/`docs/program/`
и в `main` не идут — так решено коммитом `2d3c4cbe`.

## 2. Этапы

Каждый этап закрывается строкой «готово, потому что …» с цифрой или выводом
команды, а не «вроде работает».

### Этап 0. Подготовка ПК

- Node 22.16+ (CI гоняет 24 и пол 22.16), git, Docker Desktop, Python 3 (нужен
  только `upgrade:test` для стороны 2.x), PowerShell 7 (Windows: есть; Linux: для
  `bootstrap.ps1 -Plan`).
- Для Linux-проверок на Windows-ПК: WSL2 Ubuntu или виртуалка — AppImage и `.deb`
  в WSL без графики не проверить полноценно, лучше ВМ с рабочим столом.
- Клон форка + прод как второй remote:
  ```bash
  git clone https://github.com/BreezeAreaSay/ai-dev-system.git && cd ai-dev-system
  git remote add prod https://github.com/stonebridgeway/ai-dev-system.git
  git fetch prod
  ```
- Отдельная «чистая» учётка ОС или ВМ для проверок установки: проверять установку
  на машине, где уже лежит `~/.ai-dev` разработчика, бессмысленно.

**Готово:** `node -v`, `docker version`, `git remote -v` показывают ожидаемое.

### Этап 1. Причина красного CI форка — БЛОКЕР

1. Открыть любой упавший job (например
   `https://github.com/BreezeAreaSay/ai-dev-system/actions/runs/41127546202`).
2. Если в логе нет ни одного шага (job «failed» за секунды, сообщение про
   billing / spending limit / account locked) — это инфраструктура: Settings →
   Billing → Actions, или включить Actions в форке. Код не трогать.
3. Если падает конкретный шаг — снять лог и отдать GPT по **промпту П2**.
4. Альтернатива, если минуты форка чинить не хочется: прогнать CI в проде — открыть
   PR в прод сразу как черновик (draft) и смотреть проверки там. Но тогда этап 2
   обязателен до перевода PR из draft.

**Готово:** на последнем коммите `main` форка (или на draft-PR в проде) все задания
`ci.yml`, `docker-publish.yml` validate/validate-browser/unix-launcher,
`desktop-windows.yml` build, `desktop-macos-linux.yml` — зелёные.

### Этап 2. Автоматические гейты на ПК — БЛОКЕР

Раздел 3.А тест-плана. Каждая упавшая проверка → **промпт П3** (дефект).

**Готово:** `npm run acceptance` печатает `0 failures out of 10` (по
CONTRIBUTING строка такая; если формат другой — записать как есть), плюс все
остальные пункты 3.А зелёные.

### Этап 3. Ручное тестирование продукта — БЛОКЕР

Раздел 3.Б тест-плана: каждый путь установки, обновление с 2.x, приложение,
клиенты, откат. Каждое расхождение с документацией → **промпт П3**. Если
документация обещает то, чего продукт не делает, — чинить либо продукт, либо
документацию, но решение записать.

### Этап 4. Исправления

По одному дефекту на ветку, промпт П3, после каждой ветки — `npm run check` у
владельца. Изменения в `docker/public-seed` → `npm run docker:seed:verify`;
в Docker-контексте → `npm run docker:prepare && npm run docker:audit`.

### Этап 5. Релизные документы

Промпт П4: дата в CHANGELOG, сверка релизных заметок с фактами из тестов
(размеры, времена, число навыков), ссылки, `Ф13`.

### Этап 6. Ревью перед PR

1. GPT — промпт П5 (самопроверка диффа `prod/main...main`).
2. Claude — ревью веток исправлений (передать: список веток/коммитов и этот план).
3. Решения владельца по Ф10 (подпись) и Ф12 (лицензия) — записаны.

### Этап 7. PR в прод

1. `main` форка = `develop` форка без рабочих документов; `git diff prod/main main --stat`
   не содержит `docs/program/`, `AGENTS.md`, `docs/DEFECTS.md`.
2. PR `BreezeAreaSay:main → stonebridgeway:main`, текст — промпт П6.
3. CI в проде зелёный. Merge **fast-forward / merge commit**, не squash: 490
   коммитов с осмысленной историей, squash её потеряет.
4. После merge: проверить, что `docker-publish` опубликовал `:edge` и ничего больше.
5. Dependabot в проде: закрыть три pip-PR (каталога нет), остальным
   `@dependabot rebase` и решать по одному после релиза (pixelmatch 8 — мажор).

### Этап 8. Релиз

1. Workflow `docker-publish` в проде → Run workflow на `main` с галкой `freeze_2x`
   (задание есть только в 3.0-версии файла, то есть после merge; условие —
   `docker-publish.yml:260`). До тега: после тега `:latest` станет 3.x и копировать
   будет нечего. Проверить:
   `docker pull ghcr.io/stonebridgeway/ai-dev-system:2` тянет образ с digest
   нынешнего `latest`.
2. Тег `v3.0.0` в проде на коммит merge.
3. Проверить: образы `:3.0.0 :3.0 :3 :latest` и `-browser`-близнецы; draft release
   с установщиком Windows, AppImage, `.deb`.
4. Скачать артефакты из draft и прогнать на чистой машине пункты 3.Б.1–3.Б.2
   (с артефактами из релиза, не из локальной сборки).
5. `npm run dist:pack` из тега → `npm publish <tgz>` (владелец). Сразу после —
   `npx ai-dev-system@3.0.0 setup` на чистой машине.
6. Текст релиза — `docs/release-notes-3.0.0.md`. Опубликовать release (с этого
   момента приложение 2.x… и 3.x начинают видеть обновление — Ф7).

### Этап 9. После релиза

- Сутки смотреть issues. Откат: `:latest` можно перевесить на `:2` (MIGRATION, «The
  way back»), npm — `npm deprecate` / dist-tag, release — снять с публикации.

### 3.Б Ручные сценарии (на чистой учётке/ВМ)

**Б1. Windows-установщик** (`AI-Dev-Setup-3.0.0.exe` из A13, потом из draft release)
- ставится без администратора; что показывает SmartScreen (Ф10);
- мастер первого запуска: находит клиентов, подключает, качает модель (с прогрессом;
  прервать сеть посреди загрузки → докачка);
- трей: здоровье; экраны проекты / расходы / навыки / журнал / консоль инструмента /
  настройки; английский и русский;
- удаление: что остаётся на диске, конфиги клиентов возвращены.

**Б2. Linux: AppImage и `.deb`** — то же, что Б1; плюс автообновление AppImage
(проверяется только после публикации релиза, Ф7).

**Б3. npx** — до публикации: `npx --yes ./dist/<tarball>.tgz setup` (сверить имя файла
после A11); после — `npx ai-dev-system setup`. Проверить `--yes`, `--clients=…`,
`--no-clients`, `--model`; без терминала конфиги клиентов не пишутся без `--clients`.

**Б4. Docker** — `sh ./bootstrap.sh` (Linux), `.\bootstrap.ps1` (Windows): клиент
получает рабочую запись; сессия = контейнер; время старта на новом томе и на
повторном (в заметках: 1.6–2.5 с и ~1 с); размер образа (в заметках: 716 MB).
Вариант `-browser` для Frontend QA.

**Б5. Клиенты** — Claude Code, Claude Desktop, Cursor, VS Code, Codex, Gemini CLI
(какие есть на ПК): `ai-dev clients install`, клиент видит инструменты; чужие
серверы и комментарии в конфиге целы байт в байт; `.backup-<время>` рядом;
`ai-dev clients remove` возвращает как было; `ai-dev clients doctor`.

**Б6. Демон** — два-три клиента одновременно: один процесс демона (`ai-dev daemon status`:
pid, sessions, clients, memory); `kill -9` демона → текущий запрос с понятной ошибкой,
следующий поднимает новый; `AI_DEV_DAEMON=0` — работа в своём процессе.

**Б7. Модель** — `ai-dev model install | status | verify | remove | doctor`;
заблокированная загрузка (INSTALL, «When the download is blocked»); `model import`.

**Б8. Обновление с 2.x** (по `docs/MIGRATION.md`, отдельно для каждого):
- клон 2.x (`v2.0.0`) → `git pull` до 3.0 → `npm ci` → всё на месте (задачи, решения,
  индекс без пересборки), запись клиента `ai-dev-system` продолжает работать;
- Docker 2.x (`:latest` до релиза) → `bootstrap` заново → тома и проекты на месте;
- Windows 2.x → установщик 3.0;
- Python dense backend 2.x → `setup --model` переводит на ONNX.

**Б9. Откат** — MIGRATION, «The way back»: клон, Docker `:2`, npm, Windows-приложение.

**Б10. `ai-dev` CLI** — `help`, `version`, опечатка (одна фраза с ближайшей командой,
exit 2), Ctrl-C (exit 130), `backup` / восстановление, `uninstall`.

**Б11. Хуки в чужом репозитории** — supply-chain проверка перед `npm install`
пакета с известной уязвимостью; ревью безопасности перед концом сессии; оба
выключаются в `.ai-dev/policy.json`.

**Б12. Негатив** — нет сети; нет Docker; Node 20 (должен отказать с понятной фразой);
путь с пробелами и кириллицей в имени пользователя (Windows!); второй экземпляр
приложения.

## 4. Промпты для GPT

Общая шапка — вставлять в начало **каждого** промпта.

### Шапка

```text
Репозиторий: ai-dev-system (локальный MCP-сервер ai-dev-mcp-server, приложение desktop/, Docker-образ).
Ты пишешь код; тесты запускаю я сам и присылаю вывод. Не утверждай, что что-то работает, пока я не прислал вывод команды.

Прочитай перед работой: CONTRIBUTING.md (разделы «Rules for every change», «Coding standards», «How the tests are split»), ai-dev-mcp-server/docs/ARCHITECTURE.md (раздел, который относится к правке), ai-dev-mcp-server/docs/SECURITY.md если трогаешь запуск процессов.

Жёсткие правила проекта:
- Новые MCP-инструменты — только расширением в ai-dev-mcp-server/src/extensions/<area>.mjs, регистрация в src/tool-extensions.mjs. Расширение никогда не импортирует mcp-stdio.mjs.
- Модули ≤ 800 строк (MODULE_LINE_CEILING); src/mcp-stdio.mjs не растёт. Не влезает — выноси, потолки не поднимай.
- Фейковые секреты в тестах — только склейкой: ["AKIA", "B".repeat(16)].join(""). Литералом — упадёт security-гейт.
- Хуки в ai-dev-mcp-server/hooks/ — намеренная копия серверного кода: меняешь логику с одной стороны — меняй и с другой, поведение одинаковое.
- Процессы — массив аргументов, shell: false. Никаких eval, new Function, shell: true, child_process.exec, интерполяции в командную строку.
- Код, комментарии, сообщения коммитов и публичная документация — по-английски. README.ru.md и docs/ru/* — по-русски. Conventional Commits.
- Изменил поведение — обнови тесты и CHANGELOG.md (раздел [3.0.0]).
- Не трогай docs/program/, они не идут в main.

Формат ответа: 1) что нашёл (файл:строка), 2) дифф, 3) какие команды мне запустить для проверки и что я должен увидеть, 4) что ты НЕ проверил.
```

### П1. Разобраться в падении CI по логу

```text
<шапка>

Задача: CI на main падает. Вот лог упавшего задания (job: <имя>):
<вставить лог>

Определи: это инфраструктура GitHub (биллинг, лимиты, недоступный runner, отсутствующая версия action) или код/тест. Если инфраструктура — скажи, что сделать в настройках, и не предлагай правок в коде. Если код — найди причину в репозитории, предложи минимальную правку и команду, которой я воспроизведу падение локально до правки и проверю после.
```

### П2. Починить конкретный шаг CI

```text
<шапка>

Шаг CI «<имя шага>» из .github/workflows/<файл>.yml падает. Лог:
<лог>

1. Найди, какая команда шага падает, и как запустить её локально (на Windows и на Linux, если различается).
2. Найди причину. Если тест флакает (падает не каждый раз) — найди источник недетерминированности (время, порядок, порт, гонка с файловой системой), а не добавляй retry/увеличение таймаута.
3. Минимальная правка + тест, который ловил бы эту причину.
```

### П3. Дефект из тестирования (шаблон, по одному на дефект)

```text
<шапка>

Дефект, найденный ручным/автоматическим тестом 3.0:
- Где: <ОС, способ установки, версия Node>
- Шаги: <точно>
- Ожидал (по <docs/...md, раздел>): <...>
- Получил: <вывод, скриншот текстом>

Сделай:
1. Найди причину (файл:строка). Если документация обещает то, чего продукт не делает, — скажи, что правильнее чинить: продукт или документацию, и почему.
2. Сначала тест, который воспроизводит дефект (должен упасть на текущем коде) — скажи, как его запустить, чтобы я увидел падение.
```
