# 23. Эпики: родительская задача с дочерними

Пункт [3.4 плана](PLAN.md). В [gap-анализе](ECC-GAP-ANALYSIS.md) GitHub-native координация
эпиков стоит в разделе D — «не переносится», — и это относится именно к синхронизации с
GitHub, а не к самой идее.

## Идея из ECC

Команды `epic-decompose`, `epic-claim`, `epic-publish`, `epic-review`, `epic-sync`,
`epic-unblock`, `epic-validate` плюс `scripts/github-coordination.js`,
`config/github-native-coordination.json` и `scripts/work-items.js` с SQLite-хранилищем.
Координация там идёт через GitHub Issues и метки: эпик — это issue, дочерние задачи — issues
с меткой, «взять в работу» — назначение исполнителя.

Переносится форма, а не транспорт: родитель, дети, ребро `depends_on` между соседями и
родитель, который не закрывается раньше детей. GitHub не нужен — сервер работает офлайн и
ведёт задачи сам.

## Ребёнок — это задача

`decompose_task` не заводит облегчённые «подзадачи»: каждый ребёнок открывается через
`begin_task`. Значит, у него свои роутинг скиллов, свой context pack, свои критерии приёмки и
своя политика планирования, а `checkpoint_task`, `verify_task`, снимки, worktree и всё
остальное работают с ним без единой оговорки. Эпик добавляет к задачам ровно три поля и ни
одного нового жизненного цикла.

Связи пишутся после того, как все дети созданы: зависимость — это id, а id появляются только в
момент создания. Поэтому порядок такой: проверить, создать всех, связать, отметить родителя.

## Зависимости

`depends_on` ссылается на соседа по ключу (`key`) или по позиции (1, 2, 3 — это ключ по
умолчанию). Три вещи отклоняются **до** того, как создан хоть один ребёнок:

- ссылка на то, чего нет — в сообщении перечислены все допустимые ключи;
- задача, которая ждёт саму себя;
- кольцо: сообщение показывает путь, который его замыкает (`a -> c -> b -> a`).

Ромб зависимостей — не цикл: двое детей вполне могут ждать одного и того же третьего.

Причина отклонять заранее простая: порядок, который нельзя отработать, — это не «эпик с
проблемой», а набор задач, ни одна из которых не может начаться. Открыть их и разбираться
потом дороже, чем не открыть.

## Состояния и что делать дальше

| Состояние | Когда |
| --- | --- |
| `complete` | Задача закрыта |
| `blocked` | Хотя бы одна зависимость не закрыта |
| `in_progress` | Зависимостей нет или они закрыты, и по задаче уже есть чекпойнт или верификация |
| `ready` | Зависимостей нет или они закрыты, и работа не начиналась |

`next` — первое `in_progress`, иначе первое `ready`: начатое важнее просто готового, иначе
эпик превращается в набор наполовину сделанных детей.

Отдельно называется тупик: открытых детей много, но каждый ждёт другого открытого. Формально
это «ничего не готово», но по сути — ошибка в разбиении, и говорить о ней нужно прямо.

## Родитель закрывается последним

`complete_task` на родителе отклоняется, пока хоть один ребёнок не `complete`. В сообщении —
список: id, статус и текст задачи каждого незакрытого ребёнка.

Отдельный случай — ребёнок, чья запись исчезла (`~/.ai-dev/state/tasks/<id>.json` удалён).
Это тоже отказ, и по той же причине: закрыть эпик означает утверждать, что сделаны все дети, а
доказательства по этому ребёнку больше нет. Пропустить его молча — единственный способ, которым
эпик мог бы выглядеть законченным, не будучи законченным.

## Чего здесь нет

Эпик один уровень глубиной: ребёнок нельзя разбить дальше. Это не техническое ограничение, а
решение — дерево задач произвольной глубины требует своего инструментария обхода, а два уровня
покрывают ту задачу, ради которой пункт писался.

Нет и координации между исполнителями: ни `claim`, ни назначения, ни синхронизации с внешним
трекером. Один агент работает над эпиком по очереди, а параллельную работу разводит worktree на
задачу (`begin_task_in_worktree`), который у каждого ребёнка может быть свой.
