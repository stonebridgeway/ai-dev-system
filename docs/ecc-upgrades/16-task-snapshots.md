# 16. Снимки состояния задачи и откат к ходу

Пункт [3.2 плана](PLAN.md). Это же требование стоит в фазе 0 Argentum: «снимки worktree
после хода и кнопка откатить до хода».

## Идея из ECC

В ECC есть команда `checkpoint` и `lib/worktree-lifecycle.js`: состояние рабочего дерева
сохраняется перед рискованным шагом, чтобы к нему можно было вернуться. Механика там —
коммит в служебную ветку.

Ход агента заканчивается изменёнными файлами, с которыми нечего сравнить: коммита нет
(ветка принадлежит пользователю), а undo редактора не переживает сессию. Снимок закрывает
этот разрыв.

## Что такое снимок

Снимок — это один объект-коммит, на который не указывает ни одна ветка, удерживаемый ссылкой
`refs/ai-dev/snapshots/<task_id>/<n>`. Его дерево — всё рабочее дерево задачи целиком:
изменения отслеживаемых файлов (в индексе или нет), удаления и файлы, которые агент создал.

Захват: `git add --all` во временный индекс, `git write-tree`, `git commit-tree` с HEAD в
родителях. План называет здесь `git stash create` — это правильная идиома для отслеживаемых
изменений, но она записывает только их, а ход, создавший файл, как раз и стоит отменять.
Временный индекс копируется из индекса репозитория ради кэша stat (тогда `add --all` не
пересчитывает хэши всего дерева), сам индекс репозитория не переписывается.

Копия наследует **время** исходного индекса, и это не деталь. Git доверяет закэшированному
stat записи, только пока запись старше индекса, в котором лежит; запись, попавшая в тот же
секундный тик, что и запись индекса, считается «racily clean», и её содержимое перечитывается.
Копия со свежим временем эту проверку тихо выключает, и правка, не изменившая размер файла
(одна цифра на другую), попала бы в снимок как содержимое, которое она заменила. Это
воспроизводится и закрыто тестом.

`.gitignore` и `.git/info/exclude` действуют, поэтому `node_modules/` и сборка в снимок не
попадают — как и каталог `.worktrees/`, который исключает `task-worktrees.mjs`.

## Откат

`rollback_task(task_id, snapshot_id)`:

1. снимает текущее состояние (`trigger: "rollback"`) — поэтому откат обратим;
2. `git restore --source <commit> --worktree -- .` возвращает файлы снимка;
3. файлы, появившиеся после снимка, удаляются, опустевшие каталоги — тоже.

Список того, что удалять, читается **после** восстановления, поэтому правила игнорирования
берутся из самого снимка: задача, которая правила `.gitignore` и откатилась, не теряет файлы,
которые перестали игнорироваться на время. Игнорируемые файлы не трогаются никогда: снимок их
и не нёс. Вложенный репозиторий (submodule или чужой `.git` внутри дерева) git показывает одной
записью-каталогом; он остаётся на месте и попадает в ответ полем `kept_files` — его история не
принадлежит этой задаче.

Откат меняет только файлы. Индекс остаётся прежним: если агент что-то застейджил, стейдж таким
и останется — это видно в `git status`, и мы его молча не переписываем.

`snapshot_id` принимается в трёх видах: `snapshot-3`, номер `3` или коммит (полный или
сокращённый от семи символов; сокращение из одних цифр читается как коммит, а не как номер).

## Что записывается в задачу

```json
{
  "snapshot_id": "snapshot-2",
  "sequence": 2,
  "turn": 2,
  "trigger": "checkpoint",
  "label": "Извлёк роутер",
  "commit": "…",
  "ref": "refs/ai-dev/snapshots/task-…/2",
  "files": ["src/app.js", "src/router.js"],
  "file_count": 2,
  "created_at": "2026-09-12T09:00:00.000Z"
}
```

`turn` — номер чекпойнта, на котором снят снимок, то есть ход. Список файлов обрезается на
сотне путей, `file_count` остаётся точным. Откаты пишутся отдельным списком `rollbacks`:
куда, чем отменяется, сколько файлов восстановлено и удалено.

## Жизненный цикл

- `checkpoint_task` снимает состояние сам, после записи чекпойнта, с меткой из `summary`.
  Репозиторий, который нельзя снять (нет git, worktree удалён), даёт
  `snapshot: { status: "skipped", reason }` — чекпойнт при этом записывается. Отключается
  параметром `checkpoint_task(snapshot: false)`.
- `complete_task` удаляет ссылки закрытой задачи и отвечает
  `snapshots: { status: "pruned", deleted: n }`. Записи снимков остаются в задаче с
  `deleted_at` и `deleted_reason`: история ходов читается и после закрытия, восстановить
  такой снимок нельзя.
- Автоматических снимков хранится не больше пятидесяти на задачу: каждая ссылка держит целое
  дерево, и длинная задача иначе растила бы объектную базу с каждым чекпойнтом. Первыми
  уходят самые старые автоматические; снимки, снятые `snapshot_task` по имени, живут до
  закрытия задачи.
- `prune_state` (пункт 3.12 плана, ещё не сделан) удаляет снимки той же функцией
  `pruneTaskSnapshots`.

## Чего снимки не делают

Ничего не пишется в историю ветки пользователя, в его stash и в его индекс: ни коммита, ни
тега, ни записи `git stash`. Снимок не заменяет коммит — он живёт, пока живёт задача, и
исчезает вместе с ней. Ссылки лежат вне `refs/heads`, поэтому `git push` их не отправляет, а
после удаления ссылок объекты собирает обычная уборка git.
