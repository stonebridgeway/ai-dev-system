## Идея из ECC

В ECC правила пишет команда `hookify`: разговор анализируется, из повторяющихся исправлений
пользователя предлагается правило, `skills/hookify-rules/SKILL.md` задаёт формат
`name/enabled/event/pattern/action`. Инвентарь серверов — `scripts/mcp-inventory.js` с
читателями `claude-code`, `codex`, `opencode` и документ `docs/MCP-CONNECTOR-POLICY.md`.

У нас формат правил уже был — `defaultPolicy()` в `src/core/agent-hooks.mjs` пишет три правила,
а `hooks/guard.mjs` их применяет. Не было проверки: guard молча пропускает правило, шаблон
которого не компилируется, молча игнорирует событие, которого не знает, и молча понижает
незнакомый `action` до предупреждения. Правило, которое ничего не делает, выглядит в файле
ровно так же, как работающее.

## 3.9. Правила policy

`upsert_policy_rule(project_path, rule)` добавляет правило или обновляет то, у которого тот же
`id`. Проверок пять, и каждая закрывает свой способ написать правило, которое не работает:

1. **Поля.** Приняты только те, что читает guard (`id`, `event`, `pattern`, `action`,
   `message`, `enabled` плюс образцы). `conditions` из формата ECC — ошибка с перечнем
   поддерживаемого, а не молча записанное поле.
2. **Шаблон.** Компилируется теми же флагами, что и `compileRegex` в `hooks/lib.mjs`
   (регистр не учитывается). Отдельно отклоняется квантифицированная группа с неограниченным
   квантификатором внутри — `(a+)+`, `(\s*x)*`: на почти подходящей строке это экспоненциальный
   перебор, то есть подвисший guard на каждой записи файла. Проверка нарочно консервативная и
   выполняется после сворачивания экранирований и классов символов, поэтому `(a\+b)+` и
   `([+*]a)+` не считаются вложенными.
3. **Событие и действие.** Только `bash | file | all` и `warn | block` — то, что guard
   действительно различает.
4. **Дубликаты.** Второе правило с тем же шаблоном на пересекающемся событии отклоняется с
   именем первого. Тот же текст на другом событии — другое правило, это разрешено.
5. **Пример.** Новое правило (и изменение шаблона или события у существующего) обязано
   совпасть с `example`. Для правила события `file` образец собирается так же, как в guard:
   путь, перевод строки, содержимое — поэтому у файловых правил есть `example_path`.
   Необязательный `counter_example` обязан не совпасть.

Хуки нельзя импортировать из сервера — их копируют в чужие репозитории, — поэтому флаги
компиляции, текст для сопоставления и правило «всё, кроме `block`, — предупреждение»
продублированы здесь по `hooks/lib.mjs` и `hooks/guard.mjs`. Чтобы копия не разошлась молча,
последний тест модуля устанавливает пакет хуков во временный проект, пишет туда правила через
`upsert_policy_rule` и запускает настоящий `guard.mjs`: блокировка срабатывает, регистр не
учитывается, файловое правило видит путь, `enabled: false` выключает.

Образцы сохраняются в самом правиле. Это и есть ответ на «правило перестало работать»:
`list_policy_rules` прогоняет их заново и сообщает правило, которое обезвредила ручная правка,
и шаблон, который стал шире, чем задумано. Guard лишние поля игнорирует. Если сам пример похож на настоящий секрет, ответ содержит
предупреждение (`warnings`), но правило пишется: правилу про секреты нужен пример нужной
формы — а вот значение после этого стоит ротировать.

Обновление — патч: `{ "id": "warn-eval", "enabled": false }` выключает правило, не повторяя
шаблон; `changed_fields` в ответе говорит, что поменялось, а `action: "unchanged"` — что не
поменялось ничего. `dry_run` прогоняет все проверки и ничего не пишет. `remove_policy_rule`
удаляет по `id` и на неизвестном перечисляет известные.

`list_policy_rules` и `agent_hooks_status` показывают для каждого правила `effective_action` —
то, что сделает guard, а не то, что написано в файле: у выключенного правила это `none`, у
правила с незнакомым действием — `warn`.

Чего сознательно нет: промпта `hookify_from_session` из C-10 (анализ сессии → предложенные
правила). Инструменты для него — уже есть, промпт остаётся отдельной работой.

## 3.10. Инвентарь MCP

`list_mcp_servers(project_path)` читает шесть проектных источников: `.mcp.json`,
`.claude/settings.json`, `.claude/settings.local.json`, `.cursor/mcp.json`, `.vscode/mcp.json`,
`.gemini/settings.json`, `.codex/config.toml` — то есть ровно то, что пишут наши же
установщики клиентов (`scripts/install-local-mcp-clients.mjs`,
`scripts/install-docker-mcp-clients.mjs`). `include_user_scope: true` добавляет личные файлы
пользователя, включая блок `projects[<путь>]` из `~/.claude.json`; по умолчанию выключено:
это файлы человека, а не репозитория.

На сервер приходится одна запись: файлы, которые его объявляют, транспорт (`stdio`, `http`,
`sse`, `websocket` или `unknown`), имена переменных окружения, подстановки с указанием, задана
ли переменная, и состояние одобрения в Claude Code (`enabled`, `disabled`, `prompt` — из
`enableAllProjectMcpServers` и списков `enabledMcpjsonServers` / `disabledMcpjsonServers`,
локальные настройки поверх проектных).

Находки:

| Находка | Уровень | Когда |
| --- | --- | --- |
| `plaintext_secret`, `secret_*` | block | Значение под ключом, похожим на учётные данные (`env`, заголовки, `--api-key=…`, параметр запроса в url), или строка, попавшая под шаблоны секретов из `change-hygiene.mjs` |
| `insecure_url` | warn | `http://` не на localhost |
| `unpinned_remote_package` | warn | `npx -y`, `uvx`, `bunx` без закреплённой версии |
| `shell_wrapped` | warn | Сервер стартует через `bash -c` |
| `unknown_transport` | warn | Ни `command`, ни `url` |
| `conflicting_definitions` | warn | Одно имя с разными определениями в разных файлах |
| `project_servers_auto_approved` | warn | `enableAllProjectMcpServers` |
| `unreadable_config` | warn | Файл есть, но не разбирается |
| `config_parse_warning` | info | Разобран с оговоркой (JSON с комментариями, неподдержанная конструкция TOML) |

Найденный секрет **вымарывается** из того, что отчёт возвращает обратно: в `args` и `url`
значение заменено маской. Отчёт о секретах, который сам его повторяет, разносит секрет дальше —
в лог, в тикет, в pull request.

Два решения по реализации:

- **TOML своими руками.** У Codex конфиг в TOML, в Node парсера нет, а зависимости здесь
  закреплены по версиям и их две. `toml-lite.mjs` читает подмножество, которое эти файлы
  используют (таблицы, массивы таблиц, точечные ключи, строки всех четырёх видов, числа,
  булевы, массивы, inline-таблицы), а всё остальное отдаёт предупреждением с номером строки и
  продолжает разбор — файл с экзотической секцией всё равно отдаёт список серверов.
- **JSON с комментариями.** `.vscode/mcp.json` и `.cursor/mcp.json` правят руками, и комментарии
  там обычное дело. Строгий `JSON.parse` пробуется первым; если он отказал, комментарии и
  висячие запятые снимаются, а в источнике остаётся пометка. Нечитаемый конфиг — это дыра в
  отчёте, а не повод его пропустить.

Полная оценка харнесса (авто-запуск в `CLAUDE.md`, `Bash(*)` в permissions, интерполяция в
хуках, оценка A–F) — это пункт 3.22 и инструмент `scan_agent_config`; он строится на этом
инвентаре. Здесь только то, что доказывает сам конфиг.

## Фикстуры

`ai-dev-mcp-server/test/fixtures/mcp-inventory/` — проект, доведённый до типичного состояния:
один сервер объявлен трижды и двумя разными способами, токен в одном клиенте берётся из
окружения, в другом спрашивается у пользователя, внутренняя точка ещё на `http://`, один сервер
запускается через shell, одна запись не дописана. Секретов в фикстурах нет намеренно: случаи с
секретом собираются во временном каталоге конкатенацией строк, иначе их поймает
`scripts/security-check.mjs` — и любой чужой сканер, которому попадётся копия дерева.
