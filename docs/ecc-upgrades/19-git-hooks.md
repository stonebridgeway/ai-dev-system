# 19. Git-хуки через core.hooksPath

Пункт [3.20 плана](PLAN.md), позиция C-11 в [gap-анализе](ECC-GAP-ANALYSIS.md).

## Идея из ECC

`scripts/codex-git-hooks/pre-commit` и `pre-push` плюс
`scripts/codex/install-global-git-hooks.sh`: те же проверки, что делает хук агента, но через
`core.hooksPath`. Смысл в том, что hook API есть не у всех клиентов, а `git commit` есть у всех,
включая человека в терминале.

## Что появилось в коде

| Файл | Роль |
| --- | --- |
| `ai-dev-mcp-server/hooks/git-hooks.mjs` | Обе проверки: разбор staged-диффа, правила из `patterns.json`, статус верификации активной задачи |
| `ai-dev-mcp-server/src/core/agent-hooks.mjs` | Цель `git` в `install_agent_hooks`: заглушки, `core.hooksPath`, предупреждения; `git_hooks` в политике; `renderHookPatterns` отдаёт хукам ещё и leftover-правила с плейсхолдерами |

Тесты: `src/core/agent-hook-scripts.test.mjs` — разбор настроек, сверка читателя диффа с
`parseAddedLines` сервера, `scanStaged` на секретах, маркерах, языковых правилах и плейсхолдерах,
напоминание по верификации, и сквозной тест, который ставит цель `git` и делает настоящий
`git commit`: испорченный коммит отклонён, чистый проходит, чужой `core.hooksPath` не тронут.

## Что делают хуки

`pre-commit` берёт `git diff --cached --unified=0` и ищет в добавленных строках то, что гигиена
называет `block`: файл-носитель секретов, секрет в строке, маркер конфликта, сфокусированный тест
(`.only`), забытый `debugger` или `breakpoint()`. Находки печатаются как `путь:строка правило`,
коммит отклоняется.

`pre-push` читает активную задачу проекта и её последнюю верификацию. Нет верификации или
последняя провалена — предупреждение. По умолчанию именно предупреждение: человек, который
делает push, не должен упираться в наш хук, но и не должен узнавать о непройденной проверке
из code review.

Режимы в `.ai-dev/policy.json`:

```json
"git_hooks": { "pre_commit": "block", "pre_push": "warn" }
```

`block` отклоняет, `warn` печатает и пропускает, `off` молчит.

## Откуда хуки берут правила

Хук не импортирует сервер: он копируется в чужие репозитории и работает, пока сервер стоит в
контейнере. Правила приходят файлом: `install_agent_hooks` пишет `.ai-dev/hooks/patterns.json`
из тех же констант, что использует `verify_change_hygiene` (`renderHookPatterns`). Для этой
задачи в файл добавились `leftovers` (двенадцать однострочных правил с их severity, языками и
сообщениями) и `placeholder_value` — благодаря последнему `pre-commit` отличает
`password = "correct-horse-battery"` от `password = "REPLACE_ME"`, чего guard пока не делает и
поэтому пропускает правило `generic_secret_assignment` целиком.

Один кусок логики продублирован осознанно: читатель диффа. `parseAddedLines` есть и в
`src/core/change-hygiene.mjs`, и в `hooks/git-hooks.mjs`. Тест кормит обе копии одним диффом и
сравнивает результат — разойтись незаметно они не могут.

## Установка и границы

`install_agent_hooks(targets: ["git"])` пишет две заглушки в `.ai-dev/git-hooks/`, ставит им
бит исполнения и выполняет `git config core.hooksPath .ai-dev/git-hooks`.

Заглушка — три строки `sh`, а не Node-скрипт: Git for Windows запускает хуки через свой shell,
и вопрос о том, как там разрешается `#!/usr/bin/env node`, просто не возникает. Путь к
реализации относительный (`$(dirname "$0")/../hooks/git-hooks.mjs`), поэтому перенос или клон
репозитория ничего не ломает.

Чего установка не делает:

- **не отбирает чужой `core.hooksPath`.** Если он уже указывает в другое место, заглушки
  записываются, путь остаётся прежним, а в `warnings` приходит строка о том, что нужно сделать
  руками.
- **не выстраивает цепочку с `.git/hooks`.** Git смотрит в один каталог, поэтому активные
  хуки из `.git/hooks` перестанут запускаться. Каждый такой файл называется в `warnings`
  поимённо: цепочка требует абсолютного пути в заглушке, а хук, который работает через раз,
  хуже того, о котором предупредили.
- **не работает в связанном worktree**, если `.ai-dev/` не в индексе: относительный
  `core.hooksPath` резолвится от корня worktree, каталога там нет, git просто не находит хук и
  идёт дальше.

`agent_hooks_status` отвечает полями `git_hooks` (какие заглушки лежат), `core_hooks_path` (куда
git смотрит на самом деле) и `git_hooks_active` — истина только когда обе заглушки на месте *и*
git указывает именно на них.

`guard.mjs` по-прежнему блокирует `git -c core.hooksPath=… commit`: разовый обход хуков из
командной строки и настройка репозитория — разные вещи.
