# Тест обновления

Установка линии 2.x после обновления — `git pull`, `docker pull` или переустановки — должна
работать дальше или сама мигрировать, не теряя данных. Для клона это проверяет
`npm run upgrade:test`, а для тома Docker и лаунчеров 2.x — `npm run docker:upgrade-check`.

## `npm run upgrade:test`

```bash
cd ai-dev-mcp-server
npm run upgrade:test                 # база: 86aba56, main прода на старте 3.0
npm run upgrade:test -- --base <коммит> --keep
```

Нужны Node 22.16+ (на более старом проверки движка поиска на Node пропускаются), git, Python 3
(на нём работает сторона 2.x; обновлённой он не нужен) и около двух минут. Во временной папке
тест:

1. выкладывает базовый коммит как git worktree и ставит его так, как документировала 2.x,
   `npm ci --ignore-scripts`;
2. создаёт состояние пяти пользователей, у каждого свой домашний каталог:
   - **по умолчанию** — без `AI_DEV_HOME`;
   - **AI_DEV_HOME** — задан своей папкой, куда 2.x писала всё на уровень глубже, в
     `$AI_DEV_HOME/.ai-dev`;
   - **раскладка тома Docker** — окружение, которое задаёт `docker/Dockerfile`: `AI_DEV_HOME`
     внутри домашнего каталога и явные корни состояния, индекса и артефактов, без контейнера;
   - **Python dense-бэкенд** — конфиг клиента с `AI_DEV_DENSE_BACKEND=python` и `BGE_M3_PYTHON`,
     веса torch, которые 2.x скачала в `~/.ai-dev/models/bge-m3`, и векторы с отметкой
     Python-бэкенда (3.0 этот бэкенд удалила);
   - **Codex runtime** — `~/.codex/state/ai-dev-system` и папка индекса в
     `~/.codex/cache/ai-dev-system`, которыми 2.x пользовалась, когда они были, а папок `~/.ai-dev`
     не было, — при том что хуки всегда писали в `~/.ai-dev/state`;

   и для каждого: задачу с чекпоинтом, решение, инстинкт, передачу сессии, поисковый индекс с
   dense-векторами — их записывает помощник 2.x так же, как его путь ONNX записывает настоящие,
   из синтетических чисел, — хуки Claude в git-репозитории и конфиги клиентов, записанные обоими
   установщиками 2.x (локальным и Docker);
3. обновляет тот же клон до рабочего дерева, как это сделал бы `git pull`, и запускает простой
   `npm ci`;
4. запускает сервер командой из конфига клиента 2.x и проверяет: задача, её чекпоинт, решение,
   инстинкт и передача находятся; движок поиска на Node читает индекс 2.x как есть — запрос
   статуса ничего не переписывает и не трогает ни одного вектора — и видит, что изменил pull:
   skills, которые он удалил (урезание каталога 2026-10-11 убрало 2 614 коннекторов), уходят из
   реестра и больше не находятся; перестройка сохраняет байт в байт
   вектор каждого документа, который остался неизменным, а векторы ушедших и переписанных
   документов отбрасывает — среди них коннекторы Membrane, которые старые выпуски 2.x тоже
   векторизовали, — оставляя переписанные следующему прогону векторизации; поиск по словам и
   гибридный отвечают; в
   `$AI_DEV_HOME/.ai-dev` ничего не осталось, хук 2.x по-прежнему запускается — а там, где его
   копия старого пути не видит перенесённую задачу, видит её после `install_agent_hooks`;
   команда хука, которую `install_agent_hooks` пишет теперь (`/bin/sh .ai-dev/hooks/with-node.sh …`),
   работает с PATH, в котором нет ничего, кроме git; `npm run
   clients:install` переводит на 3.0 конфиги клиентов, записанные обоими установщиками 2.x, —
   `ai-dev-system` удалён, Docker-запись `ai-dev` заменена, все шесть клиентов записаны с
   резервной копией, каждая записанная команда отвечает на `initialize` с инструкциями, повтор
   ничего не меняет. Для
   пользователя Python dense-бэкенда тест проверяет ещё: `embedding_status` называет каждую
   оставшуюся настройку и одну команду, которая её заменяет; проверка здоровья предупреждает, а не
   падает; гибридный поиск отвечает, ни с чем не сравнивая векторы Python; одна команда из
   заметок — `npm run setup -- --model` с синтетической моделью вместо BGE-M3 на локальном
   зеркале, там, где был бы huggingface.co, — даёт каждому подходящему документу вектор новой
   модели, и индекс остаётся целым. Для пользователя Codex runtime — что в
   `~/.codex/state/ai-dev-system` не осталось ничего от AI Dev, задача теперь лежит в
   `~/.ai-dev/state`, перенос записан в `state/runtime-home-migration.json` с указанием, откуда, а
   хук 2.x, который в `~/.codex` не заглядывал никогда, теперь видит задачу.

Каждая проверка печатает `✓` или `✗`; последняя строка — `N of M checks passed`, и любой `✗`
даёт код выхода 1.

## Контейнерная половина: `npm run docker:upgrade-check`

```bash
cd ai-dev-mcp-server
npm run docker:upgrade-check -- --old-image ghcr.io/stonebridgeway/ai-dev-system:2 --new-image ai-dev-system:local
```

`:2` появится с выходом 3.0 — это `:latest` 2.x, скопированный в него перед тегом 3.0. До тех пор
образ 2.x — сам `ghcr.io/stonebridgeway/ai-dev-system:latest`: так его и называют — здесь и в
командах ниже. Он же тогда установщик bootstrap по умолчанию, поэтому для `bootstrap.sh --image`
записи пишет собранный вами образ 3.0: `AI_DEV_INSTALLER_IMAGE=ai-dev-system:local`. bootstrap
пробует скачать и его, так что ответ Docker «pull access denied for ai-dev-system …» ожидаем, и
берётся образ, собранный здесь.

Нужны Docker, оба образа и этот клон с базовым коммитом (`86aba56`; неполный клон получает его
командой `git fetch origin 86aba56f9d2b7ebd6e883f4774778bd0625e17e3`): лаунчер 2.x берётся оттуда.
`docker-publish.yml` запускает проверку на каждом pull request против образа апстрима — `:2`, а
пока `:2` нет, `:latest`. На временном томе и во временной
папке, которые в конце удаляются:

1. **2.x заполняет том.** Образ 2.x, запущенный через `docker/run-mcp.sh` из 2.x так, как его
   запускают конфиги клиентов 2.x, заполняет новый том (своим `cp -n` seed) и начинает задачу;
   затем skill из seed правится так, как правил бы пользователь, и добавляется собственный skill
   пользователя.
2. **Новый образ под лаунчером 2.x.** Тот же лаунчер (его холодный путь) с новым образом: сервер
   отвечает на рукопожатие своими инструкциями; задача на месте; skills в томе — skills нового seed
   плюс собственный skill пользователя: то, что поставляла 2.x и убрала 3.0, удалено, а
   исправленный skill сохранил правку, и рядом лежит `SKILL.md.seed-new`.
3. **Тёплый путь 2.x.** Runtime-контейнер нового образа, запущенный так, как его запускал
   bootstrap 2.x, по-прежнему обслуживает сессию через лаунчер 2.x; скрипт 3.0 с тем же именем
   пропускает собственное рукопожатие сервера и говорит в stderr, что он лаунчер 2.x.
4. **Запись 3.0** на том же томе, со смонтированной папкой состояния хоста: состояние тома, а с
   ним задача, переезжает туда.
5. **Путь назад так, как его пишет `bootstrap.sh --image …:2`**: образ 2.x под записью 3.0 отвечает
   и видит задачу в этой папке состояния.
6. **Снова новый образ**: то, что `cp -n` этого старта 2.x вернул в том, убирается снова, и в томе —
   skills seed и собственный skill пользователя.

Проверка печатает времена и счётчики в JSON и выходит с кодом 1 на первой не прошедшей.

**Откат** на образ 2.x после шага 4 через собственные лаунчеры 2.x (`AI_DEV_IMAGE`) находит vault,
индекс и модель, но не задачи: они теперь в папке состояния хоста, куда лаунчер 2.x сервер не
направляет. Запись 3.0, которая запускает образ 2.x, — `bootstrap.sh --image …:2`, — даёт ему эту
папку, и задачи он в ней видит. Ничего не потеряно; скопированные обратно в
том, они у 2.x есть и под его собственными лаунчерами:

```bash
docker run --rm --entrypoint sh \
  --mount type=volume,source=ai-dev-system-data,target=/data \
  --mount type=bind,source="$HOME/.ai-dev/state",target=/host-state,readonly \
  ghcr.io/stonebridgeway/ai-dev-system:2 -c 'cp -a /host-state/. /data/runtime-home/.ai-dev/state/'
```

Возврат на 3.0 отменяет то, что откат сделал с томом: `cp -n` образа 2.x вернул все skills, которые
3.0 убрала, а с ними свой манифест; следующий старт 3.0 находит этот манифест, узнаёт вернувшееся
по истории seed и убирает снова; задачи, начатые 2.x за это время,
переезжают в папку состояния хоста.

Половину, касающуюся данных, без Docker — сервер с окружением образа на данных, записанных 2.x, —
выполняет сценарий **раскладка тома Docker** в `npm run upgrade:test`.

Клон, откаченный на 2.x с заданным `AI_DEV_HOME`, снова ищет на уровень глубже и не находит ни
задач, ни индекса; ничего не потеряно, и переменные `AI_DEV_STATE_ROOT=$AI_DEV_HOME/state` и
`AI_DEV_SEARCH_INDEX_DIR=$AI_DEV_HOME/cache/search-index` для 2.x возвращают его к ним. Замер на
деревьях, которые оставляет `npm run upgrade:test -- --keep`: сервер 2.x находит задачу и 3 444
документа индекса в раскладке Docker как есть, ничего — в клоне с `AI_DEV_HOME` как есть, и то и
другое — там же с этими двумя переменными.
