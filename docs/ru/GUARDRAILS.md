# Ограничители

[← README](../../README.ru.md) · [Установка](INSTALL.md) · [Рабочий процесс](WORKFLOW.md) · [Возможности](CAPABILITIES.md)

Части системы, которые говорят «нет»: хуки, действующие на каждое действие, а не
только на инструменты, которые агент решил вызвать; файл политики, который их
настраивает; инвентаризация того, к чему подключены ваши агенты; и то, что
остаётся на вашей машине.

## Хуки

`install_agent_hooks` встраивает защиту сервера в самого агента: она работает на
каждом действии, а не только на тех инструментах, которые агент решил позвать.

```text
Используй MCP-сервер ai-dev. Вызови install_agent_hooks для ~/Dev/my-project
с targets ["claude"] и profile "standard".
```

Инструмент кладёт самодостаточные скрипты в `.ai-dev/hooks/`, политику в
`.ai-dev/policy.json` и регистрации в `.claude/settings.json` (Claude Code)
и/или `.cursor/hooks.json` (Cursor). Существующие настройки не затираются, а
объединяются: переписываются только прежние записи AI Dev. Повторный запуск
обновляет скрипты и сохраняет ваши правила. `agent_hooks_status` показывает, что
установлено.

На macOS и Linux каждая регистрация запускает свой скрипт через лаунчер —
`/bin/sh .ai-dev/hooks/with-node.sh guard.mjs bash`, — потому что редактор или
Git-клиент, открытый из Dock, не видит `PATH` вашей оболочки, и голый `node` там не
находится, если Node поставлен через nvm, fnm, Volta или Homebrew. Лаунчер берёт
сначала `AI_DEV_NODE`, затем Node, которым хуки были установлены на этой машине
(`.ai-dev/hooks/.node-path`, его git игнорирует), затем `node` из `PATH`, затем обычные
места установки; `AI_DEV_NODE`, который не исполняемый файл Node (скажем, папка `bin`),
лаунчер называет и пропускает. Лаунчер и Git-заглушки — shell-скрипты, и `.gitattributes`
рядом с ними оставляет их с LF в клоне с `core.autocrlf`. На Windows регистрации вызывают `node`: приложения, запущенные из
меню «Пуск», находят его в `PATH` пользователя. Хуки, установленные 2.x, вызывают
голый `node`: `agent_hooks_status` их считает (`bare_node_commands`), а повторный
`install_agent_hooks` их переписывает.

Хуки останавливают команду до запуска (обход git-хуков, разрушительные и
публикующие команды), останавливают запись до применения (файлы-носители
секретов, секреты в содержимом, ослабленная конфигурация линтера), форматируют
изменённые файлы, подкладывают последний handoff и открытые задачи в начале
сессии, выжимают из транскрипта запись сессии в конце, учитывают расход каждого
ответа и советуют, когда сжимать контекст. Любая ошибка хука завершается кодом 0,
поэтому сломанный хук не блокирует агента.

То, что хук пишет в конце сессии, — черновик, а не handoff: его поля получены
эвристиками по транскрипту. Поэтому `resume_session` показывает такую запись с
пометкой «не подтверждено», а `save_session` с `confirm_hook_draft: true`
превращает её в полноценную: ваши поля побеждают, остальное берётся из
черновика, сам черновик удаляется.

Хук захвата стоимости читает тот же транскрипт с другой целью: после каждого
ответа он суммирует токены сообщений ассистента, появившихся с прошлого раза, и
дописывает их в usage ledger по моделям. Он пишет токены, а не деньги:
`usage_report` считает стоимость при чтении по опубликованным тарифам Anthropic
и показывает «сегодня», «вчера», «за 7 дней», а также итоги по моделям и
задачам. Цены меняются, поэтому `model_rates` в `.ai-dev/policy.json`
переопределяет любую строку (доллары за миллион токенов), а модель без тарифа
попадает в список «без цены», а не считается бесплатной.

Три профиля:

- `minimal` — только guard на команды и файлы, запись сессии и захват стоимости.
- `standard` — по умолчанию: всё перечисленное, включая форматирование,
  подкладывание контекста при старте, советник по сжатию и проверку в конце ответа.
- `strict` — тот же набор плюс дополнительные предупреждения перед `git push`
  и `git commit --amend` и режим `fact_force`.

`fact_force` — единственный отказ строгого профиля не про опасность. Первая
правка файла за сессию отклоняется, пока агент не выписал факты, на которых она
стоит, а первая разрушительная команда — пока он не выписал путь назад:

```text
FACTS src/router.mjs
importers: src/app.mjs и src/server.mjs
api: добавляет экспорт `resolve`, ничего не удаляет
data: читает таблицу маршрутов в config/routes.json
instruction: "научи роутер разбирать вложенные пути"
```

Отказ приводит этот блок целиком, агент пишет его в том же ходе, что повторяет
правку, и повтор проходит; дальше файл считается обоснованным до конца сессии.
Гейт читает транскрипт, поэтому там, где транскрипта нет, он ничего не судит, а
после трёх отказов за сессию перестаёт спорить и только предупреждает.
`fact_force` в политике включает его где угодно и выключает в строгом профиле, а
`exempt_globs` убирает его с путей, где спрашивать не о чем.

`targets: ["git"]` ставит ещё два — не для одного клиента, а для всех:
`install_agent_hooks` пишет `.ai-dev/git-hooks/{pre-commit,pre-push}` и
направляет туда `core.hooksPath`, поэтому коммит из редактора, из скрипта и из
терминала встречает одни и те же правила. `pre-commit` отклоняет застейдженный
секрет, маркер конфликта, сфокусированный тест и забытый `debugger`; `pre-push`
говорит, если у активной задачи нет верификации или последняя провалена. Чужой
`core.hooksPath` не отбирается, а называется в предупреждении, как и каждый файл
из `.git/hooks`, который перестанет запускаться: git смотрит в один каталог, а не
в два.

### Зависимости и проверка безопасности

Вредоносный код в пакете выполняется во время установки, поэтому guard смотрит
на пакет до того, как установка его запустит. В профилях standard и strict
каждая команда `npm install|i|add`, `pnpm add`, `yarn add`, `bun add` или
`npx|pnpm dlx|yarn dlx|bunx`, в которой назван пакет из реестра, сверяется с
advisory GitHub (в том виде, в каком их отдаёт реестр npm) и с отчётами `MAL-`
из OSV:

- **малварь** отклоняется — в том числе точная версия, которую npm уже снял:
  зеркало может её по-прежнему отдавать;
- **релиз моложе 24 часов** отклоняется, с более старой версией, которую можно
  закрепить, и временем, когда этот станет доступен; моложе семи дней — предупреждение;
- **известные уязвимости high и critical** — предупреждение с первой версией вне
  их диапазонов.

Запросы идут через `HTTPS_PROXY`, `HTTP_PROXY` и `NO_PROXY` так же, как их читают npm и
curl. Проверка, которую нельзя провести — нет сети, приватный реестр, таймаут, —
предупреждает и никогда не блокирует. Установка по lockfile (`npm ci`,
`pnpm install`) пакетов не называет и не проверяется: то, что лежит в lockfile,
проверяет `run_security_scan`.

Ещё два хука делают так, что каждое изменение получает проверку безопасности, даже
если агент о ней не вспомнил. Правка `package.json`, lockfile, `.npmrc` или
`.yarnrc.yml` кладёт агенту в контекст заметку, что зависимости не проверены. А
когда после последнего `run_security_scan` (его отметка —
`.ai-dev/security/last-scan.json`) менялся код бэкенда или фронтенда, манифест
или Dockerfile, Stop-хук один раз возвращает агента запустить скилл
`ar-security-review`, прежде чем закончить.

`.ai-dev/policy.json` — место для настройки без правки скриптов:
`allow_config_edits`, `format_on_edit`, пороги сжатия, `model_rates`,
`completion_claims` (линтер заявлений о завершении: `enabled` и `waivers` из
`{ rule, reason, expires }`), `fact_force` (`enabled`, `files`, `bash`,
`expiry_minutes`, `max_denials`, `max_entries`, `exempt_globs`), `git_hooks`
(`pre_commit` и `pre_push`, каждый — `block`, `warn` или `off`), `supply_chain`
(`enabled`, `min_release_age_hours`, `warn_release_age_days`, `osv` — `false`
не отправляет имена пакетов в api.osv.dev, — `timeout_ms`, `max_packages`),
`security_review_on_stop` (`block`, `remind` или `off`) и ваши собственные
правила:

```json
{
  "profile": "standard",
  "rules": [
    {
      "id": "block-prod-migrations",
      "event": "bash",
      "pattern": "(migrate|migration).*(--prod|production)",
      "action": "block",
      "message": "Production migrations need explicit human approval."
    }
  ]
}
```

`event` — `bash`, `file` или `all`; `action` — `block` или `warn`.

### Правила без ручной правки JSON

Правило, о котором никто не доказал, что оно срабатывает, не делает ничего — и
guard об этом молчит: некомпилируемый шаблон, событие, которого он не
обрабатывает, или незнакомый `action` он пропускает или молча понижает до
предупреждения. Поэтому у блока правил есть свои инструменты:

```text
Используй MCP-сервер ai-dev. Вызови upsert_policy_rule для ~/Dev/my-project с
правилом, которое блокирует `terraform destroy`, и с примером, на котором оно обязано
сработать.
```

`upsert_policy_rule` компилирует шаблон ровно так же, как guard (без учёта
регистра), отказывает нерабочему — включая квантифицированную группу с
неограниченным квантификатором внутри, которая подвесит guard на длинной строке, —
отказывает второму правилу с тем же шаблоном на том же событии (`all` считается
любым из них) и отказывает новому или изменённому
шаблону, который не совпадает с переданным `example`, — у включённого правила:
выключенное после правки проверяется только по форме, а сопоставляется, когда его
включают. Пример сохраняется в самом
правиле, поэтому `list_policy_rules` перезапускает его и показывает правило,
обезвреженное ручной правкой, — а у выключенного правила — пример, с которым его
шаблон не совпадает: `upsert_policy_rule` не включит такое правило, пока шаблон или
пример не исправят; `counter_example` проверяется так же — на шаблон, ставший
слишком широким. Обновление — это патч, поэтому
`{ "id": "warn-eval", "enabled": false }` выключает правило — даже там, где поток
сопоставления не стартует, — а `remove_policy_rule` удаляет его. `agent_hooks_status` перечисляет все правила и
то, что guard с каждым из них сделает. Файл перечитывается на каждом вызове, так
что изменение действует сразу, без перезапуска клиента.

## К чему подключены ваши агенты

У каждого клиента свой список MCP-серверов, и каждая запись — это программа,
которая стартует вместе с редактором и отвечает на вызовы инструментов вашими
правами. `list_mcp_servers` читает их все — `.mcp.json`, `.claude/settings.json`
и `settings.local.json`, `.cursor/mcp.json`, `.vscode/mcp.json`,
`.gemini/settings.json`, `.codex/config.toml` — и выдаёт по одной записи на
сервер: какие файлы его объявляют, каким транспортом, какие переменные окружения
подставляются и заданы ли они, запустит ли Claude Code сервер без вопроса.

Секрет, выписанный в конфиг открытым текстом, — находка `block`, и в отчёте он
замаскирован, чтобы не разойтись дальше: файл лежит в репозитории, значит
значение есть в каждом клоне, и его нужно ротировать, а не просто удалить строку.
Предупреждения: обычный HTTP до удалённой точки, `npx -y` без закреплённой версии,
сервер, запускаемый через shell, запись, которую не запустит ни один клиент,
нечитаемый конфиг и одно имя сервера с разными определениями в двух файлах.
`include_user_scope: true` добавляет ваши личные `~/.claude.json` (вместе с его
блоком для этого проекта), `~/.cursor/mcp.json`, `~/.gemini/settings.json` и
`~/.codex/config.toml`; по умолчанию выключено, потому что это ваши файлы, а не
файлы репозитория.

## Локальные данные и безопасность

Образ содержит только проверенный публичный seed — правила, prompts, quality gates, разрешённые
skills, — runtime и то, что построено из этого seed: его реестр skills, отчёт о качестве,
поисковый индекс и бенчмарк маршрутизации. В него не включаются:

- пароли, токены, `.env`, ключи и пользовательские конфигурации;
- личный Obsidian Vault, `.codex`, `.ai-dev`, Git history и локальные кэши;
- `02-knowledge/Projects`, `02-knowledge/Task Runs`, индексы ваших данных, логи, backup-архивы;
- исходники и контекст ваших проектов;
- веса BGE-M3.

Данные, созданные контейнером, хранятся в локальном Docker volume `ai-dev-system-data`. Его
состояние — задачи, handoff'ы, журнал расходов — пишется вместо этого в вашу `~/.ai-dev/state`,
смонтированную в контейнер как `AI_DEV_STATE_ROOT` там, где эту папку можно делить с
пользователем образа, — так у хуков агента на вашей машине и у сервера одно состояние; где нельзя,
состояние тоже остаётся в volume. Обновление образа не перезаписывает этот volume. По умолчанию
контейнер запускается без сети, не от root, с read-only root filesystem, без Linux capabilities и с
`no-new-privileges`.

Если проекту действительно нужен интернет во время проверки, замените в записи этого клиента
`--network none` на `--network bridge` — осознанно и только пока это нужно; повторная запись
(bootstrap или `ai-dev clients install --docker`) вернёт `none`. `AI_DEV_DOCKER_NETWORK=bridge`
делает то же только для лаунчеров 2.x (`docker/run-mcp.sh`, `run-mcp.ps1`, `ClaudeMcpProxy`);
запись 3.0 эту переменную не читает.

Модель угроз самого сервера и правила, которым следует его код, —
в [ai-dev-mcp-server/docs/SECURITY.md](../../ai-dev-mcp-server/docs/SECURITY.md).
Сообщить об уязвимости: [SECURITY.md](../../SECURITY.md).
