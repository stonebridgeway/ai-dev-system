[← README](../../README.ru.md) · [Рабочий процесс](WORKFLOW.md) · [Возможности](CAPABILITIES.md) · [Ограничители](GUARDRAILS.md)

AI Dev ставится тремя способами. Все три запускают один и тот же сервер — те же инструменты, тот же
seed навыков, ту же локальную модель — и отличаются тем, что требуют от машины и где работает
сервер. Если нужно просто начать, хватит [README](../../README.ru.md#установка); здесь — всё
остальное.

## Выбор способа

| | Настольное приложение | Одна команда с Node | Docker |
| --- | --- | --- | --- |
| Для кого | человек за своим компьютером, без терминала | сервер, на котором работают агенты, с настройкой из терминала; или своя машина | сервер в контейнере: машина, где не должно быть вашего хранилища, команда на одном образе |
| Что нужно | 64-битная Windows или 64-битный Linux | Node.js 22.16+ (или 24+) и npm | запущенный Docker Desktop (Windows) или Docker Engine (Linux); на Windows ещё Node.js 22.12+ и клон репозитория — конфиги клиентов пишет Node |
| Что запустить | `AI-Dev-Setup-<версия>.exe` или AppImage / `.deb` | `npx ai-dev-system setup` | `sh ./bootstrap.sh` (Linux) или `bootstrap.ps1` (Windows) |
| Где работает сервер | на своём Node, из `~/.ai-dev/app` (`%USERPROFILE%\.ai-dev\app`) | на вашем Node, из `~/.ai-dev/app` | в контейнере на каждую сессию; данные — в томе `ai-dev-system-data` |
| Как настраивать | в окне: настройки, навыки, правила, MCP-серверы | `ai-dev` без аргументов открывает меню; или `ai-dev settings`, `skills`, `rules` ([из терминала](#настройка-сервера-из-терминала)) | те же команды через `docker run … ai-dev …` |
| Локальная модель | шаг модели в мастере | `setup --model` | один раз `docker run … ai-dev model install` |
| Обновления | предлагает приложение (Windows, AppImage) или новый пакет | та же команда, `@latest` | `docker pull` |

**macOS в разработке.** 3.0 выходит для Windows и Linux: приложения для Mac в релизе нет, а установка
из терминала и через Docker на Mac не поддерживается, пока её там не примут. Код остаётся, и CI
тестирует его на Mac, поэтому то, что эта страница говорит о macOS — его пути, Docker Desktop,
приложение для Mac, — описывает этот код, а не поддерживаемую установку.

Python не нужен ни одному из них. Два инструмента, `query_ui_ux_knowledge` и
`generate_ui_ux_design_system`, запускают собственный скрипт набора UI UX Pro Max на Python
(`python3`; на Windows — `python`; или тот, что назван в `AI_DEV_PYTHON`); без Python они отвечают,
что установить, проверка здоровья помечает `ui_ux_knowledge` пропущенной, и больше ничего не
меняется. В образе Python нет. Локальной модели он тоже не нужен: в 3.0 dense-бэкенд на Python удалён
(см. [Переход с Python-бэкенда](#переход-с-python-бэкенда)).

## Настольное приложение: Windows, Linux

Для тех, кто без терминала. Скачайте пакет для своей системы из
[релизов](https://github.com/stonebridgeway/ai-dev-system/releases) проекта:

- **Windows** — `AI-Dev-Setup-<версия>.exe`; запустите. Ставится для вашей учётной записи, без
  администратора. Неподписанный установщик при первом запуске вызывает предупреждение Windows
  SmartScreen; **Подробнее → Выполнить в любом случае** продолжает установку.
- **Linux** (x64) — `sudo apt install ./AI-Dev-<версия>-linux-amd64.deb`, чтобы появился пункт в меню;
  или `AI-Dev-<версия>-linux-x86_64.AppImage`: `chmod +x` и запустите. AppImage нужен FUSE 2, которого
  в Ubuntu 22.04 и новее нет по умолчанию (`sudo apt install libfuse2t64` на 24.04, `libfuse2` на
  22.04), а где непривилегированные пространства имён пользователя запрещены — так по умолчанию в
  Ubuntu 24.04, — она запускается без песочницы Chromium; `.deb` ставит профиль AppArmor, с которым
  песочница остаётся.
- **macOS** — в разработке: пакета для Mac в 3.0 нет. Приложение для Apple silicon собирается из клона
  (`npm run dist:mac`), без подписи и без приёмки.

Ни Node, ни Python, ни Docker не нужны: приложение несёт свой Node и сервер, который оно запускает.
Первый запуск копирует рантайм в `~/.ai-dev/app`, заполняет ваше хранилище, `~/.ai-dev/vault`, из
seed навыков и открывает мастер: папка проектов, ИИ-клиенты для подключения, локальная модель,
индекс. Перезапустите подключённых клиентов. Всё остальное меняют экраны приложения: настройки, ваши
собственные навыки (добавить папку, начать по шаблону, импортировать репозиторий навыков с GitHub),
правила защиты, хуки и инженерные правила репозитория, MCP-серверы, которые он запускает.

Обновления приходят из тех же релизов: приложение на Windows и AppImage ищут их через минуту после
запуска и каждые шесть часов, скачивают в фоне и предлагают перезапуститься; `.deb` обновляется
установкой нового пакета. Удаление на Windows спрашивает, убрать ли AI
Dev из ваших ИИ-клиентов (по умолчанию — да) и удалить ли его данные (по умолчанию — нет); на Linux
сначала выполните `~/.ai-dev/app/current/ai-dev uninstall --clients --yes`, потом удалите приложение.

Что куда ставится, почему каждый клиент запускает его через `~/.ai-dev/app/current`, командная
строка для терминала и как собрать пакеты самому (`cd desktop && npm run dist:win`, `dist:linux`) — [Установка приложения](DESKTOP.md#установка-приложения). Окно, трей и экраны —
[Настольное приложение](DESKTOP.md).

## Одна команда с Node: npx

Для своей машины — Linux или Windows; macOS в разработке — с Node.js 22.16 или новее (или 24+) и npm. В Node
22.13–22.15 и 23.x `node:sqlite` собран без FTS5, который нужен поисковому индексу: там сервер
запускается, а каждый поисковый инструмент отвечает, какая версия ему нужна.

```bash
npx ai-dev-system setup
```

`npx` запускает пакет из своего кэша, а его npm может очистить в любой момент. Поэтому `setup`
сначала ставит пакет в `~/.ai-dev/app/<версия>-<отпечаток>` — отдельную копию, каждый файл которой
сверен со списком пакета, с зависимостями из lockfile пакета (`npm ci` без установочных скриптов), —
и продолжает уже оттуда:

1. **Спрашивает**, если запущен в терминале: подключить ли найденных здесь ИИ-клиентов; скачать ли
   локальную модель (около 600 МБ); поставить ли Frontend QA (Playwright и его Chromium, для
   проверок интерфейса). `--yes` отвечает по умолчанию — клиенты да, обе загрузки нет, — а
   `--clients=<имена>`, `--no-clients`, `--model` и `--frontend-qa` отвечают заранее. Без терминала и
   без `--yes` (CI, конвейер) конфиги клиентов не трогаются, если `--clients` никого не назвал.
2. **Заполняет ваше хранилище**, `~/.ai-dev/vault`, из seed, который несёт пакет, и строит то, что
   нужно первому запуску: реестр навыков, его отчёт качества, поисковый индекс и бенчмарк
   маршрутизации.
3. **Подключает клиентов**: каждый получает одну запись, `ai-dev`, которая запускает ваш Node по
   полному пути с `bin/ai-dev.mjs mcp` этой копии, так что клиент, запущенный из Dock или меню «Пуск»,
   тоже его находит. Что пишется и как убрать это обратно —
   [Подключение к ИИ-агентам](#подключение-к-ии-агентам).
4. **Печатает проверку здоровья.**

Перезапустите подключённых клиентов — это вся установка. Остальные команды — та же командная строка,
`npx ai-dev-system <команда>` ([ниже](#командная-строка-ai-dev)); глобальная
установка, `npm install -g ai-dev-system`, даёт ей имя `ai-dev`, и `ai-dev setup`
тогда подключает клиентов к глобальной установке. Подсказки сервера пишутся для той установки,
которая у вас.

Чтобы поставить версию, собранную самостоятельно, соберите её tarball в клоне — `cd
ai-dev-mcp-server && npm ci && npm run dist:pack`, после чего `ai-dev-system-<версия>.tgz` лежит в
папке `dist/` в корне клона (`../dist` от `ai-dev-mcp-server`), — и запустите в этой папке
`npx --yes ./ai-dev-system-<версия>.tgz setup`.

**На Linux x64** установочный скрипт onnxruntime-node качает CUDA-провайдер на 236 МБ, который
сервер никогда не загружает, а без сети или за прокси эта загрузка падает; тогда npm пропускает
пакет, и локальной модели в этой установке не на чем работать. Копия, которую делает `setup`,
ставится без установочных скриптов, и её это не касается. Для глобальной установки поставьте
`ONNXRUNTIME_NODE_INSTALL=skip` перед `npm install -g`; `ai-dev model
doctor` подскажет, как вернуть пакет для вашей установки.

**Ваше хранилище.** Папку самого пакета сервер не меняет: всё, что он пишет, — реестры, карточки
проектов, заметки — уходит в `~/.ai-dev/vault`, куда копируется seed пакета. Каждая новая версия
приносит свои изменения seed по его sha256-манифесту:

- файл, который вы не трогали, заменяется;
- изменённый вами файл остаётся вашим. Если обновление тоже его изменило, версия обновления
  кладётся рядом как `<файл>.seed-new`, и `ai-dev doctor` называет каждый такой файл (проверка
  `vault_seed`), пока вы не перенесёте нужное и не удалите `.seed-new`;
- удалённый вами файл остаётся удалённым, а файл, которого в seed больше нет, удаляется, если вы его
  не меняли;
- старая версия никогда не откатывает хранилище, обновлённое новой.

Если удалить `~/.ai-dev/vault/.ai-dev-seed.json`, следующий старт начнёт заново: удалённое вернётся,
а каждый изменённый вами файл останется и будет назван, как выше.

`AI_DEV_HOME`, если задан, называет runtime home вместо `~/.ai-dev`; он попадает в запись каждого
клиента и рядом с хуками, которые `install_agent_hooks` ставит в репозиторий, так что клиент,
запущенный из Dock или меню «Пуск», — и его сервер, и его хуки — видит те же данные, что и
терминал, где запускали setup.

## Docker

Сервер работает в контейнере: каждый клиент на свою сессию запускает `docker run -i --rm …`, как это
записано в его конфиге. Этот способ — для машины, где не должно быть вашего хранилища, или для
команды, у которой один образ работает везде одинаково. В образе нет хранилища, паролей, токенов,
проектов и истории задач: сервер, Node, git, tini и gitleaks — без Python и без браузера, если не
взять вариант `-browser`.

### На macOS и Linux

Нужен запущенный Docker — Docker Desktop на macOS, Docker Engine на Linux: bootstrap проверяет его и
говорит, откуда его взять, но ничего не ставит. Серверу Node на хосте не нужен (хуки агента, если
поставить их в проект, работают на Node хоста). Из клона репозитория — или только с его
`bootstrap.sh`: больше ему ничего не нужно, если не собирать образ самому:

```bash
sh ./bootstrap.sh
```

Три шага:

1. **Docker** на месте, и его движок отвечает (на macOS скрипт запускает Docker Desktop и ждёт его).
2. **Образ** скачивается — `ghcr.io/stonebridgeway/ai-dev-system:latest`, — и сервер в нём отвечает
   на рукопожатие MCP своими instructions.
3. **Конфиги.** Их пишет образ: `ai-dev clients install --docker` работает в контейнере, который
   видит папку конфига каждого клиента и вашу папку состояния, и больше ничего из домашней папки.
   Claude Code хранит свои серверы в `~/.claude.json`, файле в самой домашней папке, поэтому его
   запись идёт через его собственный CLI (`claude mcp add-json`); если CLI нет в `PATH`, скрипт
   печатает команду. Запись получает каждый найденный здесь клиент, и последняя строка просит
   перезапустить клиентов. Если не поставлен ни один, ничего не пишется, и скрипт так и говорит:
   поставьте клиента и запустите bootstrap снова или назовите клиента в `--clients` (`-Clients` у
   `bootstrap.ps1`, который на Windows делает то же самое), — и заканчивает строкой «AI Dev is ready;
   no AI client is connected to it yet.» (Где `bootstrap.ps1` не может прочитать ответ установщика —
   только на хосте, который не даёт переключить консоль на UTF-8, — вместо этого выводятся слова самого
   установщика, его подсказка `--clients=`, а за ними строка самого `bootstrap.ps1` с просьбой
   перезапустить клиентов.) С `--skip-client-install` (`-SkipClientInstall`) не пишется ни
   один конфиг, а последняя строка говорит, что конфиги клиентов оставлены как были.

Чтобы запустить образ, собранный из вашего клона, а не опубликованный, — со своими изменениями или
на машине, которой не достать реестр, — соберите и поставьте его одним шагом, которому Node здесь не
нужен: контекст сборки готовит контейнер `node:24-bookworm-slim`:

```bash
sh ./bootstrap.sh --build-local   # собирает ai-dev-system:local из клона и ставит его
```

Он собирает образ сам, а не скачивает его из реестра. С Node и npm сборка может быть и отдельным
шагом:

```bash
cd ai-dev-mcp-server && npm run docker:build && cd ..   # даёт ai-dev-system:local
sh ./bootstrap.sh --image ai-dev-system:local --allow-stale-image
```

Названный ему образ bootstrap всё равно сначала пробует скачать, поэтому «Registry pull failed …
Installed from a stale image» для образа, собранного здесь, тогда ожидаемо. `--project-path` и
`--clients` подходят к обоим.

Для другой папки проектов и части клиентов:

```bash
sh ./bootstrap.sh --project-path "$HOME/Dev" --clients "codex,cursor,vscode"
```

После этого перезапустите клиентов. Повторный запуск безопасен: конфиг, который уже запускает этот
образ, остаётся как есть, том — хранилище, индекс, модель — сохраняется, и папки проектов и модели,
которые монтируют записи, в том числе записи 2.x, тоже, если `--project-path` или `--model-path` не
называют другие; bootstrap говорит, какие оставил. Чтобы собрать образ из клона, а не скачивать: `sh ./bootstrap.sh --build-local`. Клиент, чей конфиг не удалось записать,
называется, а остальные всё равно пишутся; тогда код выхода 1, и рантайм-контейнер 2.x остаётся, пока
не переписан каждый конфиг. Конфиг, который — ссылка в репозиторий dotfiles,
пишется через неё: каждая папка, куда она ведёт, монтируется установщику по пути, который пишет
ссылка, — но ссылка в саму домашнюю папку, в папку выше неё или в корень не открывается, а папка,
которую Docker не монтирует (вне общего доступа Docker Desktop), стоит одного этого клиента.

Если реестр недоступен, а в локальном кэше есть более старая копия образа, bootstrap останавливается
и не ставит её, а говорит, когда эта копия собрана, и её digest. Поставить её всё равно — осознанный
выбор: `sh ./bootstrap.sh --allow-stale-image` (`-AllowStaleImage` на Windows).

Путь назад, на 2.x, — `sh ./bootstrap.sh --image ghcr.io/stonebridgeway/ai-dev-system:2`; и он
оставляет папки, которые монтируют прежние записи. У образа 2.x нет своего установщика, поэтому конфиги для него пишет образ 3.0
или новее: `AI_DEV_INSTALLER_IMAGE`, по умолчанию `ghcr.io/stonebridgeway/ai-dev-system:3` — линия 3.x,
которую откат `:latest` на 2.x не трогает. Он
скачивается — копия, закэшированная до 3.0, была бы образом 2.x — и используется, только если в нём
есть установщик; иначе bootstrap останавливается и просит его. `:2` появится с
выходом 3.0 — это `:latest` 2.x, скопированный в него перед тегом 3.0. До тех пор образ 2.x — сам
`ghcr.io/stonebridgeway/ai-dev-system:latest`, он же установщик по умолчанию, поэтому установщиком
должен быть собранный вами образ 3.0: `AI_DEV_INSTALLER_IMAGE=ai-dev-system:local sh ./bootstrap.sh
--image ghcr.io/stonebridgeway/ai-dev-system:latest`. bootstrap сначала пробует скачать и образ
установщика, поэтому ответ Docker «pull access denied for ai-dev-system …» тут ожидаем: собранного
здесь образа нет ни в одном реестре, и bootstrap продолжает с копией, которую находит здесь.

### На Windows

Нужен Docker Desktop — установленный; скрипт сам запускает его и ждёт движка, — и Node.js 22.12 или
новее: конфиги клиентов пишет Node, потому что Linux-контейнер не может записать файл по пути Windows.
Если чего-то нет, скрипт говорит, как поставить (`winget install Docker.DockerDesktop`, `winget
install OpenJS.NodeJS.LTS`), и останавливается; сам он ничего не ставит. После `git clone` откройте
PowerShell в корне клона и запустите:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1
```

Он скачивает опубликованный образ, проверяет, что сервер в нём отвечает на рукопожатие MCP, и
прописывает запись `ai-dev` в каждого найденного ИИ-клиента: `docker run -i --rm …`, который клиент
запускает сам. Папка проектов — `%USERPROFILE%\AI-Dev-Projects`, она монтируется как `/workspace`:
Linux-контейнер не может держать путь Windows, поэтому на Windows сервер видит проекты там. Ничего
больше не компилируется: 2.x собирал на вашей машине прокси на C# для Claude, а лаунчеры, которые 2.x
копировал в `C:\ProgramData\AI-Dev-System`, только обновляются, если они там есть (см.
[Обновление и переход с 2.x](#обновление-и-переход-с-2x)).

Чтобы запустить образ, собранный из вашего клона, а не опубликованный, соберите и поставьте его
одним шагом — контекст сборки готовит Node, который скрипту нужен и так:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 -BuildLocal
```

Он собирает `ai-dev-system:local` и не скачивает образ из реестра. Или соберите образ отдельным
шагом и назовите его:

```powershell
cd ai-dev-mcp-server; npm run docker:build; cd ..
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 -Image ai-dev-system:local -AllowStaleImage
```

Тогда предупреждение «Registry pull failed … Installed from a stale image» для образа, собранного
здесь, ожидаемо.

Папка состояния, `%USERPROFILE%\.ai-dev\state`, — общая с сервером, как на macOS, но на Windows общий в
ней только журнал использования. Сервер видит проект как `/workspace/<имя>`, а хуки — как
`C:\…\<имя>`: для каждой стороны это два разных проекта, а задачи и передачи сессий хуков хранятся
по проекту. Stop-хук не напоминает о задаче, которую начал сервер, а сервер не видит передачу, которую
записали хуки.

Для другой папки проектов и части клиентов:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\bootstrap.ps1 `
  -ProjectPath "D:\Projects" `
  -Clients "codex,cursor,vscode"
```

После этого перезапустите ИИ-клиента.

### Что запускает клиент

Каждую сессию — так bootstrap пишет на macOS и Linux:

```text
docker run -i --rm --read-only --tmpfs /tmp … --network none --security-opt no-new-privileges:true --cap-drop ALL
  --mount type=volume,source=ai-dev-system-data,target=/data
  --mount type=bind,source=~/.ai-dev/state,target=/ai-dev-state --env AI_DEV_STATE_ROOT=/ai-dev-state
  --mount type=bind,source=~/AI-Dev-Projects,target=~/AI-Dev-Projects
  ghcr.io/stonebridgeway/ai-dev-system:latest
```

- **Проекты по своему пути** (по умолчанию `~/AI-Dev-Projects`): путь, который называет агент, —
  тот, что открывает сервер. 2.x монтировал их в `/workspace`, и путь хоста был «не найден».
- **Состояние, которое ведут хуки агента**, — то же, что у сервера: ваш `~/.ai-dev/state`. Хуки
  работают на вашей машине; при одном состоянии Stop-хук видит задачу, начатую сервером. Для
  этого пользователь контейнера — uid 1000, пользователь образа — должен быть вами: на macOS его
  сопоставляет Docker Desktop, на Linux это uid первого пользователя, — и на Linux установщик сначала
  пробует: контейнер образа пишет файл в папку, и файл должен оказаться вашим. С другим uid, а также
  там, где Docker сопоставляет пользователей контейнера другим (rootless Docker, userns-remap,
  Podman), сервер держит состояние в томе и не может писать в ваши проекты — установка хуков или
  правил туда отклоняется, — как в 2.x; `ai-dev clients install --docker` говорит об этом, и на такой
  машине выбирайте [npx](#одна-команда-с-node-npx).
- **Один контейнер на сессию**, он стартует примерно за секунду; долгоживущего контейнера больше нет,
  а тот, что держала 2.x (`ai-dev-system-runtime-<uid>`), `bootstrap.sh` удаляет.
- **Новый том** начинает с того, что построил бы первый запуск, — реестра навыков, его отчёта
  качества, поискового индекса, бенчмарка маршрутизации, — уже собранного в образе. Docker заполняет
  новый том, когда на нём стартует первый контейнер; второй клиент, запущенный мгновением позже, ждёт
  конца этого копирования, не дольше 20 с, прежде чем читать том.

### Образ и его теги

```bash
docker pull ghcr.io/stonebridgeway/ai-dev-system:latest
```

Теги: `:latest` — новейший выпуск, тег `vX.Y.Z` — не пререлиз — новейшей
линии; `:edge` идёт за `main`; выпуск — это ещё и `:X.Y.Z`, `:X.Y` и `:X`. `:2` — линия 2.x и путь
назад: в него перед тегом 3.0 копируется `:latest` 2.x, а потом его двигает только тег `v2.Y.Z` —
вместе с `:2.Y` и `:2.Y.Z`, но никогда не `:latest`. Frontend QA нужен браузер: вариант `-browser`
(`:latest-browser`, и `-browser` после любого другого тега) несёт Chromium — примерно на 0,8 ГБ больше
0,7 ГБ основного. Тег, который назван в конфиге клиента, — это то, что запустит его следующая сессия:
`docker pull` и есть обновление.

Или соберите его из клона:

```bash
cd ai-dev-mcp-server
npm ci
npm run docker:prepare
npm run docker:audit
npm run docker:build
npm run docker:smoke -- --image ai-dev-system:local
```

Контекст сборки, `.docker/build-context`, — это дистрибутив, который делает `npm run dist` (`ai-dev/`,
при сборке сверенный файл за файлом со своим `distribution.json`), рядом с Dockerfile и entrypoint —
никогда не корень репозитория и не хранилище.

### Записи без bootstrap

С Node на хосте — npx или клон — команду, которую запускает bootstrap, можно запустить самому:

```bash
npx ai-dev-system clients install --docker --projects "$HOME/Dev"
```

Остальное задают `--image`, `--model`, `--volume` и `--clients`; `--dry-run` ничего не пишет;
`clients entry cursor --docker …` печатает одну запись в JSON для клиента, которого настраиваете
вручную; `clients doctor` затем запускает каждую запись и проверяет, что сервер отвечает. Лаунчеры
2.x — `docker/run-mcp.sh`, `run-mcp.ps1` — по-прежнему запускают образ для конфигов, которые их
называют, до 4.0.

### Чем контейнер исполняет ваши проверки

В контейнере `run_quality_gate` и `verify_task` выполняют команды из `.ai-dev/quality-gate.md` вашего
проекта **Node образа** — сейчас 24, — а не той, что стоит у вас. Команда, которая ведёт себя
по-разному в разных мажорных версиях Node, будет расходиться с вашим терминалом, и виноват в этом не
гейт. Типичный случай — `node --test test/`: начиная с Node 21 позиционные аргументы — это шаблоны
glob, поэтому каталог запускается как файл теста и скрипт падает сам по себе, хотя под Node 20
проходил.

`run_quality_gate` сообщает, какая Node выполнила команды, в `runtime.node` и `runtime.exec_path`, а
упавшая команда несёт `hint`, если причина — из тех, что гейт распознаёт. Переписывать ваши команды
он не будет.

Ещё контейнер работает с `--network none`, а из шести сканеров безопасности без сети работает только
`gitleaks` — он есть в образе. Поэтому скан там — один сканер, а не шесть; полная матрица — в
[docker/README.md](../../docker/README.md). Скан, в котором не запустился ни один сканер, возвращает
`unchecked`, а не `pass`. git в образе доверяет смонтированным проектам, чьи бы они ни были на хосте:
2.x видел проект другого пользователя как вовсе не репозиторий.

### Docker Compose

Конфиг клиента запускает `docker run` сам; Compose — для тех, кто держит контейнеры в нём.
Скопируйте `docker/compose.local.example.yaml` в `docker/compose.local.yaml`, задайте
`AI_DEV_PROJECT_PATH` — папку ваших проектов (монтируется по своему пути) — и назовите опубликованный
образ: без `AI_DEV_IMAGE` сервис собирает `ai-dev-system:local` из `.docker/build-context`, который
делает `npm run docker:prepare`:

```bash
AI_DEV_IMAGE=ghcr.io/stonebridgeway/ai-dev-system:latest \
  docker compose -f docker/compose.yaml -f docker/compose.local.yaml run --rm -T ai-dev-mcp
```

`compose.local.yaml` и `docker/.env` игнорируются Git, потому что могут содержать локальные пути.

## Подключение к ИИ-агентам

Не правьте эти файлы вручную, если клиента покрывает установщик: это делают `setup` (npx, клон),
мастер приложения Windows и bootstrap (Docker), а отдельно — `clients install`.

| Клиент | Файл конфигурации | Запись |
| --- | --- | --- |
| Claude Code | `~/.claude.json` или `$CLAUDE_CONFIG_DIR/.claude.json`, если переменная задана (тогда Claude Code читает только его) | `mcpServers.ai-dev`, с `type: "stdio"` |
| Claude Desktop | macOS `~/Library/Application Support/Claude/claude_desktop_config.json`; Windows `%APPDATA%\Claude\claude_desktop_config.json` и собственная копия сборки из Microsoft Store в `%LOCALAPPDATA%\Packages\Claude_*`; сборки для Linux — `~/.config/Claude/claude_desktop_config.json` | `mcpServers.ai-dev` |
| Cursor | `~/.cursor/mcp.json` | `mcpServers.ai-dev` |
| VS Code | `Code/User/mcp.json` в папке пользовательской конфигурации (`%APPDATA%`, `~/Library/Application Support`, `~/.config`) | `servers.ai-dev`, с `type: "stdio"` |
| Codex | `~/.codex/config.toml` или `$CODEX_HOME/config.toml` | `[mcp_servers.ai-dev]`, с `startup_timeout_sec = 120` и `tool_timeout_sec = 3600` |
| Gemini CLI | `~/.gemini/settings.json` | `mcpServers.ai-dev` |

Локальная запись — установщика, npx, клона — запускает Node по полному пути, затем `bin/ai-dev.mjs
mcp` установки: клиент, запущенный из Dock или меню «Пуск», не видит `PATH` вашей оболочки, и голый
`node` там не найдётся, если Node поставлен через nvm, fnm, Volta или Homebrew. Запись Docker сама
запускает `docker run`, с CLI Docker по полному пути по той же причине.

Что установщик делает с файлами:

- **Какие клиенты.** По умолчанию — все, что здесь установлены (их папка есть).
  `--clients=cursor,vscode` называет их явно (`claude` — оба приложения Claude), и клиент, названный
  так, пишется, даже если не найден.
- **Больше ничего не меняется.** Файл правится там, где стоит запись: все остальные серверы,
  комментарии (VS Code и Gemini принимают JSONC) и строки остаются байт в байт. В Codex таблица
  сервера находится вместе с подтаблицами и при любом написании имени.
- **Безопасно.** Файл пишется через временный и переименование, после проверки, что клиент его тем
  временем не сохранил; прежние байты остаются рядом как `<файл>.backup-<время>`. Конфиг, который —
  символическая ссылка (репозиторий dotfiles), пишется через ссылку.
- **Одно имя.** Запись `ai-dev-system` — её писал локальный установщик 2.x — удаляется, а запись
  `ai-dev` другой установки (Docker или локальной) заменяется; вывод говорит, какая. У каждого клиента
  один `ai-dev`: выигрывает установка, подключившая его последней.
- **Сломанный файл — одна неудача.** Он остаётся как был и называется со строкой, где он ломается;
  остальные клиенты всё равно пишутся, а команда выходит с кодом 1.
- **Повтор ничего не меняет.** Второй запуск говорит `No changes`.

`clients list` показывает каждого клиента и что запускает его запись. `clients doctor` запускает
команду каждой записи так, как это сделал бы клиент, и проверяет, что она отвечает на `initialize` с
instructions, — это проверка на случай, когда клиент показывает сервер упавшим; у каждой команды 30
секунд, `--timeout=<секунды>` даёт больше. `clients remove` убирает `ai-dev` (и `ai-dev-system`)
обратно: файл, который с тех пор больше ничто не меняло, получает то, что в нём было, кроме любой
записи `ai-dev` или `ai-dev-system`, которую заменила установка, — записи 2.x, Docker или другой
установки: она не возвращается (её байты остаются в `<файл>.backup-<время>`, который установка
оставила рядом); из любого другого файла вырезается только запись. `--dry-run` показывает, что
изменили бы `install` или `remove`.

### Записи Docker вручную

Для клиента, которого не покрывает ни один установщик, или чтобы прочитать, что они пишут.
`clients entry <клиент> --docker --projects <папка>` печатает точную запись для этой машины.
Замените `/home/you/Dev` или `C:\Dev` папкой, где лежат ваши проекты, и не коммитьте эти значения в
Git.

**Codex** — добавьте в пользовательский `config.toml`, здесь так, как пишет Linux. `command` — полный
путь к `docker`, который находит ваш `PATH`: на Linux обычно `/usr/bin/docker`, на macOS с Docker
Desktop — `/usr/local/bin/docker` (какой именно, скажет `command -v docker`):

```toml
[mcp_servers.ai-dev]
command = "/usr/bin/docker"
args = [
  "run", "-i", "--rm", "--read-only", "--tmpfs", "/tmp:rw,exec,nosuid,size=512m", "--shm-size", "1g",
  "--network", "none", "--security-opt", "no-new-privileges:true", "--cap-drop", "ALL",
  "--mount", "type=volume,source=ai-dev-system-data,target=/data",
  "--mount", "type=bind,source=/home/you/.ai-dev/state,target=/ai-dev-state", "--env", "AI_DEV_STATE_ROOT=/ai-dev-state",
  "--mount", "type=bind,source=/home/you/Dev,target=/home/you/Dev",
  "ghcr.io/stonebridgeway/ai-dev-system:latest"
]
startup_timeout_sec = 120
tool_timeout_sec = 3600
```

Монтирование папки состояния и её переменная есть только там, где пользователь контейнера, uid 1000, —
это вы; см. [Что запускает клиент](#что-запускает-клиент). Перезапустите Codex и убедитесь, что сервер
`ai-dev` появился в списке инструментов MCP.

**Cursor, Claude Desktop, Claude Code и Gemini** используют JSON со свойством `mcpServers`. Добавьте
или влейте блок ниже в их конфигурацию — здесь так, как пишет Windows, с проектами в `C:\Dev`,
которые сервер видит как `/workspace`:

```json
{
  "mcpServers": {
    "ai-dev": {
      "command": "C:\\Program Files\\Docker\\Docker\\resources\\bin\\docker.exe",
      "args": [
        "run", "-i", "--rm", "--read-only", "--tmpfs", "/tmp:rw,exec,nosuid,size=512m", "--shm-size", "1g",
        "--network", "none", "--security-opt", "no-new-privileges:true", "--cap-drop", "ALL",
        "--mount", "type=volume,source=ai-dev-system-data,target=/data",
        "--mount", "type=bind,source=C:\\Users\\you\\.ai-dev\\state,target=/ai-dev-state",
        "--env", "AI_DEV_STATE_ROOT=/ai-dev-state",
        "--mount", "type=bind,source=C:\\Dev,target=/workspace",
        "ghcr.io/stonebridgeway/ai-dev-system:latest"
      ]
    }
  }
}
```

`bootstrap.ps1 -Clients claude` пишет оба файла Claude: `%USERPROFILE%\.claude.json` для Claude Code и
`%APPDATA%\Claude\claude_desktop_config.json` для Claude Desktop вместе с собственной копией сборки из
Microsoft Store в `%LOCALAPPDATA%\Packages\Claude_*`. На macOS и Linux bootstrap даёт Claude Code запись
через его собственный CLI (`claude mcp add-json`). Шаблон для macOS и Linux —
[docker/mcp-config.example.json](../../docker/mcp-config.example.json): замените `/home/YOU` своей
домашней папкой, а путь к Docker — тем, что отвечает `command -v docker`. После изменения конфигурации
перезапустите клиента полностью.

**VS Code** — создайте `.vscode/mcp.json` в рабочем репозитории или добавьте тот же сервер в
пользовательские настройки MCP VS Code: блок выше под `servers` вместо `mcpServers`, с `"type":
"stdio"` рядом с `command`. Перезагрузите окно. На Windows сервер видит проекты в `/workspace`:
вызывайте `begin_task` с `/workspace/my-project`; на macOS и Linux он видит их по своему пути.

## Локальная модель

У гибридного поиска две половины: поиск по словам, который работает везде без настройки, и
dense-поиск на локальной модели BGE-M3 — то, что позволяет поиску понимать вопрос, а не совпадать
словами. Среда ONNX приходит с каждой установкой; веса — нет: около 600 МБ, их скачивают один раз и
сверяют с sha256 манифеста, а оборванная загрузка продолжается с того же байта. Работает модель в
Node, без Python.

| | |
| --- | --- |
| Установщик Windows | шаг модели в мастере: **Скачать** или **Импортировать из папки…** |
| npx | `npx ai-dev-system setup --model` |
| Docker | `docker run --rm -it --network bridge --mount type=volume,source=ai-dev-system-data,target=/data ghcr.io/stonebridgeway/ai-dev-system:latest ai-dev model install` |
| Клон | `npm run setup -- --model` |

Каждая из команд ставит модель и строит векторы документов, которые уже есть в индексе. `model status`
говорит, что установлено и что остановилось на полпути, `verify` хеширует каждый файл, `remove` удаляет
файлы модели и больше ничего, а `model doctor` проходит весь путь в шесть этапов и называет тот, где
остановилось. Для Intel Mac нет сборки среды ONNX (в onnxruntime-node 1.30 её нет), поэтому там модель
не работает и каждый инструмент говорит об этом; поиск работает по словам.

**Место под неё.** Загрузка не начинается на диске, где не помещаются веса и ещё 512 МБ запаса, — она
говорит, сколько нужно и сколько есть, а не забивает диск до последнего байта. Диск, где они
помещаются, но мало что остаётся, тоже подходит — загрузка один раз предупреждает, что может идти
медленно.

### Если загрузка закрыта

Загрузка читает `HTTPS_PROXY`, `HTTP_PROXY` и `NO_PROXY` так же, как npm и curl, — учётные данные
пишутся в URL прокси, `http://user:password@proxy:3128`, — без `NODE_USE_ENV_PROXY`. Прокси, который
входит по NTLM или Kerberos, а не по паролю, достигается через локальный пересылающий прокси, который
сам выполняет вход, например cntlm или px, названный в `HTTPS_PROXY`; ошибка говорит об этом, когда это
так. Зеркало Hugging Face — одна переменная:

```bash
AI_DEV_MODEL_MIRROR=https://hf-mirror.com npx ai-dev-system setup --model
```

`AI_DEV_MODEL_MIRROR` (или `HF_ENDPOINT`, который читают другие инструменты Hugging Face) пробуется
первым, затем huggingface.co; источник, который отказал, передаёт загрузку следующему, и тот
продолжает тот же частичный файл. Каждый файл сверяется с манифестом, какой бы источник его ни прислал.
В контейнер их передают через `--env`.

Пути нет совсем? Скопируйте модель с машины, где она есть, — папку, папку выше неё, кэш Hugging Face
или `.zip` любого из них:

```bash
npx ai-dev-system model import /media/usb/bge-m3-onnx.zip
```

В том Docker — смонтировав её на этот один запуск: `docker run --rm -it --mount
type=volume,source=ai-dev-system-data,target=/data --mount
type=bind,source=/media/usb,target=/import,readonly ghcr.io/stonebridgeway/ai-dev-system:latest ai-dev
model import /import/bge-m3-onnx.zip`.

### Модель на хосте — для Docker

Модель, которая уже есть на хосте, — `~/.ai-dev/models/bge-m3-onnx`, куда её кладут npx и клон, —
можно смонтировать только для чтения вместо копирования в том: назовите папку *выше* неё,
`~/.ai-dev/models` (`--model-path` у bootstrap, `-ModelPath` на Windows, `--model` у `clients install
--docker`):

```bash
sh ./bootstrap.sh --model-path "$HOME/.ai-dev/models"
```

Образ читает `/models/bge-m3-onnx` первым, если там что-то есть, — и сессии, и его собственные
проверки, — поэтому неполную модель там исправляют на хосте или убирают
монтирование. Папка, в которой лежат сами файлы модели (`pytorch_model.bin`, `config.json`, `onnx/`), —
это значение переменной до 2.1, и каждый установщик отказывает в ней с объяснением, а не монтирует её
уровнем глубже. Если `bge-m3-onnx` — ссылка на другой диск, запись монтирует саму ссылку, и Docker
проходит по ней на хосте: в контейнере одна ссылка вела бы в никуда; ссылку, которая и на хосте ведёт в
никуда, установщик отклоняет. Каждая сессия монтирует то, куда ведёт ссылка, поэтому, пока этот
диск отключён, Docker не запускает ни одной — в журнале клиента будет «bind source path does not exist».
Об этом говорит запись конфигов, а там, где установлена командная строка, `ai-dev clients doctor`
называет запись, чьей смонтированной папки нет. Файлы и папки модели должен читать
пользователь образа, uid 1000; если не может, это говорят отчёт старта, `embedding_status`, `ai-dev setup` и
`ai-dev model status`. Векторы документов строятся с ней, без загрузки и без сети,
командой `docker run --rm -it --mount type=volume,source=ai-dev-system-data,target=/data --mount
type=bind,source=<папка выше bge-m3-onnx>,target=/models,readonly
ghcr.io/stonebridgeway/ai-dev-system:latest ai-dev setup --model`.

### Если нужен образ с весами внутри

Опубликованный образ без них остаётся небольшим, и для поставки по умолчанию это правильно. Машине без
сети или образу, который раздают команде, чтобы каждый не качал веса сам, нужна модель внутри. Это
ваша сборка, а не дистрибутива: Dockerfile из двух строк и одна команда сборки:

```dockerfile
# Dockerfile.bge — собирается из папки, где лежат веса
FROM ghcr.io/stonebridgeway/ai-dev-system:latest
COPY --chown=node:node bge-m3-onnx/ /models/bge-m3-onnx/
```

```bash
docker build -f Dockerfile.bge -t ai-dev-system:bge-bundled "$HOME/.ai-dev/models"
```

Результату не нужны ни монтирование, ни переменная: `/models/bge-m3-onnx` уже там, где образ смотрит
первым. Всё остальное — `--network none`, корень только для чтения, непривилегированный пользователь —
остаётся как было.

### Переход с Python-бэкенда

2.x умел вести dense-поиск на виртуальном окружении Python с torch и весами на 2,3 ГБ
(`--dense-python`, `AI_DEV_DENSE_BACKEND=python`, образ, собранный с `INSTALL_BGE_M3=1`). В 3.0 он
удалён. Переход — одна команда: в клоне `npm run setup -- --model`, с npx — `npx
ai-dev-system setup --model`.

Она ставит модель ONNX и заново строит векторы документов: векторы Python-бэкенда — векторы другой
модели и с вопросами ONNX не сравниваются, поэтому они ждут этого запуска и им заменяются; остальной
индекс сохраняется. Пока команда не запущена, поиск работает без своей dense-половины. Ни одна из
оставшихся настроек — `AI_DEV_DENSE_BACKEND=python`, `BGE_M3_PYTHON`, `AI_DEV_EMBEDDINGS_PYTHON`,
`AI_DEV_PYTHON_BASE`, `BGE_M3_PYTHON_REVISION`, `BGE_M3_MODEL_DIR` — больше не читается; проверка
здоровья называет каждую найденную, а папку весов torch `~/.ai-dev/models/bge-m3` можно удалить.
`--dense-python` по-прежнему работает как имя и делает то же, что `--model`, а сборка Docker с
`INSTALL_BGE_M3=1` получает сообщение о том, что его заменило. Терминальный вид BuildKit
сворачивает вывод законченного шага — на экране сообщение оставляет `--progress=plain`, — а шаг из
кэша не печатает ничего, так что при следующей сборке того же дерева сообщение видно только с
`--no-cache`.

### Как убедиться, что заработало

Проверка здоровья `embedding_backend` пишет `skipped` и что запустить, пока модели нет, и `ok`, когда
она есть (команда для каждой установки — в [Если что-то не работает](#если-что-то-не-работает)).
Подробнее, чем эта строка, говорит инструмент `embedding_status`: может ли модель работать и почему.
Ответ — `installed` и `available`, `reason` — предложение, а не флаг, а `partial` перечисляет загрузки,
остановившиеся на полпути. В `dense_backend.onnx` поле `missing` перечисляет файлы, которых нет, а
`mismatched` — файлы, которые есть, но не совпадают с закреплённым экспортом: первое значит, что
монтирование не дошло, второе — что байты не те; `unreadable`, если есть, говорит, почему этот
пользователь вообще не смог прочитать модель. Всё, что осталось от
Python-установки 2.x, лежит в `dense_backend.legacy`, и проверка здоровья остаётся `warn`, пока это не
убрано. Затем `search_index_status` показывает `dense_documents` против `dense_pending_documents`: у
нового индекса векторов нет ни у одного документа, пока модель не установлена (а для модели,
смонтированной с хоста, — пока не запущен `ai-dev setup --model`, как выше).

## Демон и настройки

Как обслуживается клиент — протокол в обоих случаях один:

| | |
| --- | --- |
| `ai-dev mcp` | То, что запускает локальная запись. Передаёт клиента **демону** — одному тёплому серверу на всех клиентов пользователя: его запускает первый клиент, а через 30 минут без клиентов он уходит сам (`AI_DEV_IDLE_TIMEOUT_MS`). Индекс и модель в памяти один раз, а не по разу на клиента, и у состояния один писатель. Рукопожатие проходит насквозь, вместе с instructions, а каждая сессия работает в окружении своего клиента — его PATH, прокси, сертификаты. Клиенты с разным кодом, Node или данными (другая копия AI Dev, другая Node, другой `AI_DEV_VAULT_ROOT`) получают по своему демону; два написания одной папки — одна папка. Упавший демон заменяется новым при следующем запросе клиента; если демон не запускается, клиента обслуживает его собственный процесс, а причина пишется в stderr. |
| `AI_DEV_DAEMON=0` в `env` клиента, `npm start` в клоне, запись 2.x (`node …/src/server.mjs`) | Отдельный stdio-процесс на клиента, как в 2.x. |
| Запись Docker | Один контейнер на сессию, без демона. |
| `ai-dev daemon status \| stop \| start \| run` | pid, сессии, память и журнал (`~/.ai-dev/logs/daemon.log`), а также все остальные демоны runtime home и чем каждый отличается; `stop` останавливает их все — следующий запрос клиента запустит новый; `run` — работа в терминале. |

Адрес демона выбирается случайно при каждом запуске и вместе с секретом записывается в
`~/.ai-dev/run/daemon-<сборка>.json`, который можете прочитать только вы; каждое подключение доказывает,
что знает секрет, и демон доказывает это в ответ (см.
[SECURITY.md](../../ai-dev-mcp-server/docs/SECURITY.md#the-daemon) *(на английском)*). Если путь домашней
папки слишком длинный для сокета, сокет ложится в `$XDG_RUNTIME_DIR/ai-dev` или `/tmp/ai-dev-<uid>`.

**Настройки.** `~/.ai-dev/config.json` хранит то, что меняет настольное приложение, `ai-dev settings`
— или инструмент `settings_set`: профили возможностей (`AI_DEV_PROFILES`), зеркало модели (`AI_DEV_MODEL_MIRROR`), папку
модели (`BGE_M3_ONNX_DIR`), время простоя демона (`AI_DEV_IDLE_TIMEOUT_MS`, там — в минутах), папку
проектов, запускает ли настольное приложение демона при своём старте (`daemon_autostart`), и язык
интерфейса. Его читает каждая команда `ai-dev`, запущенная после, — а значит, и каждый клиент,
подключённый локальной установкой, и подключение настольного приложения к демону; переменная, заданная
в окружении, по-прежнему главнее. `settings_set` говорит, когда действует каждое изменение: зеркало — со
следующего скачивания, и в той же сессии; папка модели и профили — в сессиях, начатых после: поиск
демона загрузил свою папку при старте, поэтому клиент переподключается, чтобы взять новую, и для неё
запускается свой демон; время простоя — со следующего запуска демона. До тех пор `settings_get`
отвечает тем, что действует в сессии, а изменение показывает в `pending`, и инструменты модели не
кладут её в папку, которую сессия оставляет. Значение проверяется до записи; ставшее неверным
`settings_get` называет, и оно не применяется. Профили — это то, что получает каждый агент без своего
`AI_DEV_PROFILES`, поэтому `control`, который включают явно, в них быть не может. Инструменты, которыми
приложение управляет установкой — состояние, настройка, модель, клиенты, журналы, настройки, — это
профиль `control`, который включают явно: [CONTROL-API.md](../../ai-dev-mcp-server/docs/CONTROL-API.md)
*(на английском)*.

## Командная строка ai-dev

У каждой установки одна командная строка: `npx ai-dev-system <команда>`, `ai-dev
<команда>` после глобальной установки, `npm run ai-dev -- <команда>` в клоне,
`~/.ai-dev/app/current/ai-dev <команда>` после настольного приложения на macOS и Linux,
`& "$env:USERPROFILE\.ai-dev\app\current\ai-dev.cmd" <команда>` в PowerShell после установщика
Windows (в cmd — `"%USERPROFILE%\.ai-dev\app\current\ai-dev.cmd" <команда>`) и `docker run --rm
-it --mount type=volume,source=ai-dev-system-data,target=/data <образ> ai-dev <команда>` в образе.

| Команда | Что делает |
| --- | --- |
| `ai-dev` | В терминале — меню над всем, что ниже настраивается и меняется ([из терминала](#настройка-сервера-из-терминала)); иначе — этот список. |
| `ai-dev setup` | Строит то, что нужно первому запуску, подключает клиентов, с `--model` — локальную модель ([npx](#одна-команда-с-node-npx)). |
| `ai-dev clients list \| install \| remove \| doctor \| entry` | Запись `ai-dev` в каждом клиенте ([Подключение к ИИ-агентам](#подключение-к-ии-агентам)). |
| `ai-dev settings [list \| get \| set \| reset \| path]` | Файл настроек: профили, папка и зеркало модели, время простоя демона. |
| `ai-dev skills search \| show \| mine \| add \| new \| remove \| import \| rebuild \| check` | Библиотека навыков, и ваши собственные. |
| `ai-dev rules list \| add \| on \| off \| remove \| hooks \| packs \| install` | Правила защиты репозитория, его хуки агента, его инженерные правила. |
| `ai-dev servers [--mine]` | MCP-серверы, которые ИИ-клиенты запускают для репозитория, и что проверить, прежде чем им доверять. |
| `ai-dev status` | Состояние в нескольких строках: модель, индекс, клиенты, проверки не в порядке. |
| `ai-dev model status \| install \| import \| verify \| remove \| doctor` | Локальная модель ([Локальная модель](#локальная-модель)). |
| `ai-dev mcp` | То, что запускает клиент: его stdio-сессия MCP, которую обслуживает демон. |
| `ai-dev daemon start \| stop \| status \| run` | Один тёплый сервер, которому передаются все клиенты. |
| `ai-dev doctor` | Проверка здоровья в JSON; `--dense-smoke` ещё и запускает модель один раз. |
| `ai-dev backup`, `ai-dev restore` | Хранилище и состояние одним архивом, и обратно ([RECOVERY.md](../../ai-dev-mcp-server/docs/RECOVERY.md) *(на английском)*). |
| `ai-dev uninstall` | Убирает рантайм настольного приложения с компьютера: это запускает удаление на Windows, а на macOS и Linux — вы сами перед удалением приложения. |
| `ai-dev help [команда]` | Все команды и их параметры. |

Каждая команда выходит с кодом 0 — сделано, 1 — не получилось, 2 — неверный вызов, 130 — остановлено
Ctrl-C; `uninstall` добавляет 3 — что-то занято — и 4 — данные оставлены. Опечатка в команде или
параметре получает ответ раньше, чем что-либо прочитано или перенесено.
`node ai-dev-mcp-server/scripts/ai-dev.mjs`, CLI из 2.x, по-прежнему выполняет все команды, с пометкой
в stderr, до 4.0.

## Настройка сервера из терминала

На сервере, где работают агенты, настольного приложения нет: всё, что меняют его экраны, — это
команды, а `ai-dev` без аргументов в терминале — и по SSH тоже — открывает меню над ними. Введите
номер и Enter; `b` — назад, `q` — выход. Каждый выбор запускает одну из команд ниже с вашими ответами
и печатает её (`$ ai-dev settings set daemon_idle_minutes 0`), так что тот же шаг можно положить в
скрипт.

```bash
ai-dev                                   # меню
ai-dev status                            # что работает, что нет, что сделать
ai-dev settings                          # все настройки: действующее значение и откуда оно
ai-dev settings set profiles core,coding # что получают агенты; папку можно задать относительно, ~ — домашняя
ai-dev settings set daemon_idle_minutes 0   # держать демона, пока его не остановят
ai-dev settings reset model_mirror       # вернуть значение по умолчанию
```

`settings set` проверяет значение до записи и говорит, когда оно подействует: зеркало — сразу,
профили и папка модели — в ИИ-сессиях, начатых после, время простоя — со следующего демона
(`ai-dev daemon stop` останавливает текущего). Переменная, заданная в окружении, по-прежнему главнее,
и команда об этом говорит.

**Навыки.** Ваши лежат рядом с пришедшими с AI Dev, в источнике custom хранилища; обновление их не
трогает, а поиск и маршрутизация видят изменение сразу.

```bash
ai-dev skills search "review a pull request"    # найти; ai-dev skills show <имя> — прочитать
ai-dev skills new release-notes "Write release notes from the merged pull requests of a version."
ai-dev skills add ./my-skills/deploy-check      # папка со SKILL.md (--replace — заменить свой)
ai-dev skills mine                              # ваши; --all — и пришедшие с AI Dev
ai-dev skills remove deploy-check --yes         # только ваш: навык из поставки не удаляется
ai-dev skills import https://github.com/owner/skills --select   # репозиторий навыков, через политику импорта
```

**Правила репозитория** — в нём, или укажите его через `--project <путь>`:

```bash
ai-dev rules                                    # правила защиты, которые соблюдают хуки агента
ai-dev rules add no-force-push --pattern 'git push .*--force' \
  --example 'git push origin main --force' --message 'Never force-push.'
ai-dev rules off no-force-push                  # on, off, remove <id>
ai-dev rules hooks install --profile standard   # хуки, которые их соблюдают (по умолчанию для Claude Code)
ai-dev rules install --dry-run                  # инженерные правила: .ai-dev/rules, .claude/rules, AGENTS.md…
ai-dev servers --mine                           # MCP-серверы из его конфигов и ваших
```

Правило проверяется на своём примере до сохранения. Каждая команда принимает `--json` для скрипта, а
`ai-dev help <команда>` перечисляет её параметры.

## Обновление и переход с 2.x

| Установка | Обновление |
| --- | --- |
| Установщик Windows | Его предлагает приложение: **Перезапустить и обновить до …** в трее, или оно ставится при **Выходе**. |
| npx | `npx ai-dev-system@latest setup`: новая копия ставится рядом со старой, записи переходят на неё, а две последние выбранные копии остаются, так что клиент, который ещё работает на предыдущей, её сохраняет. |
| Docker | `docker pull ghcr.io/stonebridgeway/ai-dev-system:latest`: следующая сессия запустит его. Повторный bootstrap делает то же и переписывает то, что изменилось в записях, оставляя папки проектов и модели, которые они монтируют, — и `AI_DEV_PROJECT_PATH` и `AI_DEV_MODEL_PATH` записи 2.x, — если `--project-path` (`-ProjectPath`) или `--model-path` (`-ModelPath`) не называют другие. |
| Клон | `git pull`, затем `cd ai-dev-mcp-server && npm ci && npm run setup`. |

Установка 2.x — клон, лаунчеры Docker, прокси на C# для Claude на Windows — продолжает работать после
обновления, а то, что она оставила, переносится или называется при старте сервера: `AI_DEV_HOME`
уровнем глубже, записи клиентов `ai-dev-system`, хуки, которые зовут голый `node`, навыки и состояние
тома Docker, Python-бэкенд модели. Что меняется, что переносится само, что требует одной вашей команды
и как вернуться: **[Переход с 2.x на 3.0](MIGRATION.md)**. `npm run upgrade:test` проверяет всё это на
клоне 2.x, а `npm run docker:upgrade-check -- --old-image <образ 2.x> --new-image <образ>` — часть Docker
на томе 2.x и его лаунчерах ([Тест обновления](UPGRADE-TEST.md)).

В `~/.ai-dev/state` — то, что делили сервер и хуки. |

Ваши проекты не трогаются никогда.

## Если что-то не работает

Проверка здоровья говорит, что не так и что запустить:

| Установка | |
| --- | --- |
| Установщик Windows | экран **Статус** или `& "$env:USERPROFILE\.ai-dev\app\current\ai-dev.cmd" doctor` в PowerShell (`"%USERPROFILE%\.ai-dev\app\current\ai-dev.cmd" doctor` в cmd) |
| npx | `npx ai-dev-system doctor` |
| Docker | `docker run --rm --network none --mount type=volume,source=ai-dev-system-data,target=/data ghcr.io/stonebridgeway/ai-dev-system:latest ai-dev doctor` |
| Клон | `npm run -s doctor` |

Клиент показывает сервер упавшим: `clients doctor` запускает каждую запись так, как это сделал бы её
клиент, и проверяет ответ. Если Docker Desktop не может скачать образ за VPN или корпоративным DNS,
настройте прокси или DNS в Docker Desktop; не кладите пароли прокси в Dockerfile, Git, аргументы
сборки или файлы проекта. Уже скачанный образ работает без доступа в интернет. Подробнее об образе —
сканеры в контейнере, Compose, GHCR — в [docker/README.md](../../docker/README.md).

## Общий сервер

Сервер, на котором работают агенты многих людей, — Argentum Workspace, VPS команды — держит одну
копию AI Dev и запускает её в сессии каждого человека от его пользователя ОС. Саму копию только
читают: хранилище, состояние и демон у каждого свои, в его `~/.ai-dev`.

- **Пакет npm**, поставленный в папку, которую пользователи могут читать, так и работает.
- **Клон** — тоже. Запущенный пользователем, который не может в него писать, он заполняет
  `~/.ai-dev/vault` этого пользователя из своего `docker/public-seed`, как пакет — из своего seed.
  `AI_DEV_VAULT=home` просит того же там, где в клон писать можно: задайте её всем, чтобы записи
  того, кто собирал клон, не жили в папке, которую заменит следующая сборка.
- **`setup` каждому не нужен.** Хранилище без реестра скиллов получает его при первом запросе,
  которому он нужен, примерно за две секунды. `setup` по-прежнему подключает собственные
  клиенты человека и скачивает модель.

Сессия запускает `node <установка>/ai-dev-mcp-server/bin/ai-dev.mjs mcp` на Node 22.16 или новее.
С `AI_DEV_PROFILES=core` в окружении агент получает 25 инструментов, около 5 700 токенов описаний,
вместо 135 и около 35 000 ([Возможности](CAPABILITIES.md)).

**Argentum Workspace.** Его сессии запускают `claude` с `--strict-mcp-config`, поэтому записи,
которые пишет `ai-dev clients install`, там не читаются. Сервер добавляется в «Настройки ·
Инструменты» → «Сложные подключения» → «Сервер из исходников»:

| Поле | Значение |
| --- | --- |
| Репозиторий | `https://github.com/stonebridgeway/ai-dev-system/tree/v3.0.0/ai-dev-mcp-server` — метка или ветка без `/`: Argentum Workspace клонирует через `git clone --branch` |
| Установка | `npm ci`, как он угадывает |
| Сборка | нет |
| Запуск | `env AI_DEV_VAULT=home AI_DEV_PROFILES=core node bin/ai-dev.mjs mcp` — угадывает он `node bin/ai-dev.mjs`, а это печатает справку |

Замер: клон собран `npm ci` от одного пользователя ОС в чистом окружении, сервер запущен от другого
через `sudo -n -u` той же строкой запуска, что у Argentum Workspace. Сборка — 330 МБ (Argentum
Workspace разрешает 1 ГБ). Первая сессия нового
участника подключается за 2,2 с, его первый `prepare_project` идёт 3,2 с — хранилище заполняется и
реестр строится; `begin_task` … `complete_task` проходят, в сборку не пишется ничего; следующая
сессия подключается за 0,2 с. У каждого участника остаётся демон на 90–180 МБ, пока 30 минут не
будет ни одной сессии (`AI_DEV_IDLE_TIMEOUT_MS`).

## Из клона

Для работы над самим AI Dev. Из корня клона:

```bash
cd ai-dev-mcp-server
npm ci
npm run setup
```

`npm ci` не запускает установочные скрипты зависимостей: их выключает `.npmrc` пакета. Важен один —
скрипт onnxruntime-node: он скачивает CUDA-провайдер, который сервер не загружает, и падает без сети
или за прокси; `npm install` ведёт себя так же. `npm run setup` — это
[тот же setup](#одна-команда-с-node-npx), что у npx, на месте: записи клиентов называют
`bin/ai-dev.mjs` этого клона, а без хранилища сервер читает встроенный seed, `docker/public-seed`.
Записи, которые писала 2.x, продолжают работать: `node <клон>/ai-dev-mcp-server/src/server.mjs` —
по-прежнему точка входа. Процесс разработки и ворота — [CONTRIBUTING.md](../../CONTRIBUTING.md)
*(на английском)*.
